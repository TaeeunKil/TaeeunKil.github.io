# 검수 기준과 사례

사용자가 제공한 한국어 정리의 전체 주제와 사례를 검수 질문으로 재구성했다. 아래 전후 문장은 별도 표기가 없는 한 이 스킬을 위해 작성한 예시이며 원문 인용이나 검증된 실험 결과가 아니다. 실제 수정에서는 초안에 있는 사실만 사용한다.

## 1. 장황한 도입과 본문 앞의 장애물

제목과 첫 세 문장에서 대상 독자와 읽을 이유를 찾는다. 읽을 이유는 기술 습득뿐 아니라 새로운 관점, 실패 경험, 재미있는 이야기일 수도 있다. 역사나 개발 계기를 일괄 삭제하지 말고 현재 독자의 이해에 필요한 위치로 옮긴다.

**문제 예시**

> 소프트웨어 개발에서 테스트는 중요하다. 나 역시 오랫동안 테스트에 관심이 있었다. 최근 프로젝트에서 여러 고민을 하다가 테스트에 대해 정리하기로 했다.

**수정 예시**

> Go 테스트가 실패했을 때 실제값과 기대값을 헷갈렸다면, 변수 이름을 `got`과 `want`로 나눠보자. 이 글에서는 두 값을 구분해 실패 메시지를 읽기 쉽게 만드는 예를 살펴본다.

원문의 Go 테스트 사례는 대상 언어와 빠르게 배울 기술을 초반에 드러낸다는 점이 핵심이다. 검증 없이 몇 초 만에 배운다는 약속을 복사하지 않는다.

도입이 좋아도 긴 자기소개, 부제, 장식 이미지, 인용문이 핵심을 뒤로 밀 수 있다. 각 요소가 독자의 이해나 흥미에 기여하는지 확인한다. 결과 화면이나 문제를 보여주는 이미지는 오히려 도입을 강화할 수 있으므로 일괄 삭제하지 않는다.

## 2. 독자의 사전지식 가정

개념을 다른 개념으로 설명할 때 그 비교 대상이 독자에게 익숙한지 확인한다. 원문에서 Jellyfin을 익숙한 스트리밍 서비스와 연결한 사례는 이러한 설명 방식의 예다. 비교는 이해를 돕는 범위에서 쓰고 기능·보안 특성이 완전히 같다는 인상을 주지 않는다.

**Docker 입문 글의 문제 예시**

> Docker는 cgroups와 namespaces를 활용하는 도구다. BSD jails를 생각하면 쉽다.

**수정 예시**

> Docker는 앱과 실행에 필요한 의존성을 이미지로 묶어, 다른 환경에서도 비슷한 실행 조건을 재현하도록 돕는 도구다. Dockerfile에는 이미지를 만드는 절차를 텍스트로 남긴다.

입문자에게 낯선 개념 여러 개로 하나를 설명하지 않는다. 반대로 컨테이너 격리를 분석하는 전문가 글에서는 cgroups와 namespaces가 필요한 핵심 내용일 수 있다. “어디서나 완전히 동일하게 실행된다” 같은 과장으로 단순화하지 않는다.

검수 전에 짧게 기준을 잡을 수 있다.

- 기준 독자: 웹 앱을 배포해봤지만 컨테이너는 처음 쓰는 동료.
- 이미 아는 것: 앱 실행, 의존성 설치, 환경변수.
- 설명할 것: 이미지와 컨테이너의 차이, Dockerfile의 역할.

이 목록은 실제 독자 정보가 없으면 가정임을 밝힌다. 모든 용어를 사전처럼 정의하지 말고 문장을 이해하는 데 필요한 설명을 해당 위치에 둔다.

## 3. 외부 링크에 설명 떠넘기기

링크를 누르지 않고도 현재 논지를 따라갈 수 있는지 읽어본다. 툴팁에만 있는 정의도 같은 문제다. 설치 파일 다운로드처럼 실제 작업에 필요한 링크와, 설명을 대신하는 링크를 구분한다.

**문제 예시**

> DB 접근은 [방화벽](https://docs.freebsd.org/en/books/handbook/firewalls/)으로 제한하면 된다.

**수정 예시**

> 방화벽 규칙으로 DB에 접속할 수 있는 출발지와 포트를 제한한다. 예를 들어 앱 서버에서 오는 DB 접속만 허용하는 방식이다. 구체적인 규칙 문법은 사용 중인 방화벽의 문서에서 확인할 수 있다.

원문의 FreeBSD 매뉴얼 사례가 보여주는 문제는 한 단어를 이해하려고 방대한 자료를 읽게 한다는 데 있다. 연결된 문서 전체를 요약할 필요는 없다. 정의·현재 문맥에서의 역할·필요한 조건만 본문에 두고 링크는 심화 자료로 유지한다. 이 짧은 예시를 완전한 DB 보안 지침처럼 취급하지 않는다.

## 4. 이전 편을 읽었다는 전제

검색으로 이 글부터 들어온 독자도 현재 문제와 핵심 결론을 이해할 수 있는지 확인한다. 시리즈 표시나 전편 링크 자체를 금지하지 않는다.

**문제 예시**

> 지난 편에서 만든 스마트 캐시를 기억할 것이다. 이번에는 그 방식의 문제를 해결한다.

**수정 예시**

> 여러 요청이 만료된 캐시를 동시에 갱신하면 같은 DB 조회가 반복될 수 있다. 이번 글에서는 갱신을 한 요청만 맡도록 만드는 방법을 살펴본다. 앞선 글의 캐시는 조회 결과를 일정 시간 저장하는 구조였다.

직접 만든 용어는 필요한 위치에서 다시 정의하고, 전편 전체 대신 현재 글에 필요한 상태·가정·결과를 요약한다. 운영체제 제작이나 연속 실습처럼 이전 코드가 필수라면 필요한 버전·파일·완료 상태를 명시한다. 긴 선행 학습을 완전히 없앨 수 있다고 약속하지 않는다.

## 5. 과도한 격식과 목소리 소실

행위자와 실제 행동을 찾기 어렵게 만드는 수동형·명사형·추상어를 고친다. 단어가 격식 있다는 이유만으로 삭제하지 않는다.

**문제 예시**

> 프로젝트의 안정성 제고를 위한 다양한 정적 분석 도구의 활용이 수행되었다.

**수정 예시**

> 프로젝트에서 정적 분석 도구 몇 개를 써봤다.

실제로 어떤 도구를 썼고 무엇을 발견했는지 초안에 있다면 이어서 구체화한다. 없으면 도구명, 버그 수, 성능 개선 수치를 만들어 채우지 않는다.

원문에서 Joel Spolsky, Kathy Sierra, Terence Eden, Raymond Chen은 자연스러운 자기 목소리의 사례로 제시된다. 그들의 문체를 복제할 필요는 없다. 작성자의 시행착오, 판단 이유, 적절한 유머를 보존하고 상투적인 AI식 도입과 결론을 새로 붙이지 않는다. 개인적인 경험을 지우는 무조건적인 객관화도 피한다.

## 6. 모바일 넘침과 읽기 편한 화면

본문의 논리와 화면의 가독성을 별도로 확인한다. 원문이 제안한 Chrome·Firefox 모바일 미리보기를 활용할 수 있다. 두 브라우저를 모두 사용할 수 없다면 실제 확인 범위만 기록한다.

- 좁은 화면에서 본문 전체를 좌우로 움직이며 읽어야 하는가?
- 고정 너비 이미지, 긴 코드, 표, URL이 페이지 전체 폭을 늘리는가?
- 코드나 표 내부의 가로 스크롤과 페이지 전체의 가로 넘침을 구별했는가? 코드 줄을 억지로 꺾어 의미를 손상시키지 않는가?
- 글꼴, 크기, 줄 간격, 배경과 글자색이 실제로 읽기 편한가? 밝은/어두운 테마가 있다면 확인한 테마를 명시했는가?
- 대비는 색 이름으로 판단하지 않고 도구로 확인했는가? 접근성 규격 충족을 주장하려면 해당 기준과 측정 근거가 있는가?

Atkinson Hyperlegible은 원문에 나온 글꼴 선택지이지 필수 적용 항목이 아니다. 한국어 글에서는 한글 글리프와 대체 글꼴도 함께 확인해야 한다. 원저자의 모바일 방문 비율을 사용자 블로그의 통계로 가져오지 않는다.

URL이나 화면이 없으면 “모바일 가독성 통과”로 표시하지 않는다. 텍스트 검수 완료와 화면 미확인을 구분한다.

## 7. 짧게 쓰기와 설명 삭제의 구분

이 절은 사용자가 제공한 GeekNews의 geulway 댓글을 바탕으로 보완한 기준이다. 문제 해결 글에서는 증상 → 확인한 환경 → 해결한 변경을 도입에 압축하면 대상 독자가 적용 가능성을 판단하기 쉽다. 아래 값은 설명을 위한 가상 사례다.

**짧지만 부족한 예시**

> 타임아웃을 늘려 오류를 해결했다.

**조건을 보존한 예시**

> Nginx를 거치는 보고서 다운로드 요청이 약 60초 뒤 504로 끝났다. 확인한 환경에서 보고서 생성에는 약 90초가 걸렸고, 해당 경로의 `proxy_read_timeout`을 120초로 바꾼 뒤 다운로드가 완료됐다.

이때 값을 실제 초안의 관측값으로 바꿔야 한다. 시간제한 변경이 근본 해결인지 임시 대응인지도 원문에 따라 유지한다. 이것이 모든 504 오류의 해결책이라고 일반화하지 않는다.

## 8. 수정안 비교 예시

A안이 짧아도 환경이 빠져 적용 여부를 알 수 없고 B안에는 조건이 남아 있다면 B안을 선택할 수 있다. 반대로 같은 조건을 반복하는 문장만 추가됐다면 긴 쪽이 더 좋지는 않다.

결론 예시: “B안은 오류가 발생한 경로와 처리 시간을 남겨 독자가 자신의 상황과 비교할 수 있다. A안보다 길지만 이 정보는 유지하는 편이 낫다. 다만 마지막의 일반적인 서버 안정성 설명은 현재 해결 과정과 연결되지 않아 줄일 수 있다.”

원문 근거가 없으면 이런 평가를 꾸며내지 않는다. 동일한 판단 기준을 양쪽에 적용하고, 장점과 손실을 함께 설명한다.
