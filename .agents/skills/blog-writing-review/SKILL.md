# 개발 블로그 글 검수

불필요한 읽기 부담은 줄이되, 이해·재현·적용 판단에 필요한 정보와 작성자의 목소리는 보존한다. 짧음, 격식, 매끄러움 자체를 품질로 취급하지 않는다. GPT 단독으로 수행하며 JeV나 별도 평가 시스템을 요구하지 않는다.

## 입력과 작업 범위

- 사용자가 지정한 초안·파일·URL을 읽는다. 대상이 없으면 검수할 글을 요청한다. 저장소 전체를 임의로 고치지 않는다.
- 대상 독자와 글의 목적이 없으면 초안에서 추정하고 짧게 밝힌다. 판단에 결정적인 정보만 질문한다.
- 검수 요청에는 근거와 수정 예시를 제공한다. 실제 파일 수정·전체 재작성은 사용자의 요청 범위에 맞춘다. 검수만으로 게시·커밋을 수행하지 않는다.
- 글의 언어와 기존 문체를 따른다. 한국어 해요체·합니다체·한다체를 무조건 하나로 바꾸지 않는다.

## 검수 방법

1. **독자와 약속:** 누구에게 어떤 이해·기술·관점·이야기를 주는 글인지 한 문장씩 정한다. 기준 독자가 알 만한 개념과 설명이 필요한 개념을 구분한다. 실제 지인이 지정되면 그 사람을 기준으로 삼고, 없으면 독자상을 가정한다.
2. **본문 점검:** 제목과 첫 세 문장의 가치 전달, 핵심까지의 거리, 사전지식 가정, 링크와 전편 의존, 문체를 확인한다. 구체적인 판단과 예시가 필요하면 [검수 기준과 사례](references/editorial-examples.md)의 관련 절을 읽는다. 포괄적 검수라면 모든 절을 읽는다.
3. **근거 있는 수정:** 문제마다 원문 위치 또는 짧은 발췌 → 해당 독자가 겪을 불편 → 최소 수정안 → 보존할 정보를 연결한다. 취향과 이해를 막는 문제를 구별하고 영향이 큰 문제부터 제시한다. 문제가 없으면 억지로 만들지 않는다.
4. **정보 보존:** 수정 전후에 사실, 버전·환경, 실패 조건, 재현 절차, 수치·단위, 코드 의미, 제한사항, 출처, 실제 경험이 유지되는지 확인한다. 빠진 사실은 확인 필요로 표시한다. 직접 해보지 않은 실험·경험·결과를 만들지 않는다.
5. **화면 검수 분리:** URL이나 실행 가능한 페이지가 제공되고 확인할 수 있다면 모바일 넘침, 이미지·코드·표, 글꼴과 대비를 실제 화면에서 확인한다. 텍스트만 있으면 화면 검수는 미확인으로 남긴다. 확인한 브라우저와 화면 크기만 보고하고 양쪽 브라우저를 모두 검사한 척하지 않는다.

기술적 오류 검증과 글쓰기 검수를 구별한다. 문장을 다듬었다고 기술적 사실까지 검증된 것으로 표시하지 않는다. 사실 확인이 필요한 핵심 주장은 적절한 공식 자료로 확인하거나 불확실성을 남긴다.

## 판단 우선순위

- 정확성과 적용 조건을 문장 길이보다 우선한다.
- 설명은 기준 독자가 이해할 만큼 제공한다. 전문가 글에 기초 설명을 일괄 추가하지 않는다.
- 첫 세 문장은 독자와 가치를 확인하는 기준이다. 문장 수를 맞추려고 억지 약속이나 상투적 개요를 넣지 않는다.
- 독립적으로 이해할 수 있게 하되, 실제 연속 실습의 필수 선행 조건은 짧고 명확하게 밝힌다.
- 자연스러운 목소리는 반말, 농담, 유명 작가 흉내를 뜻하지 않는다. 작성자의 구체적인 선택과 관찰을 살린다.

## 결과 형식

글과 요청의 크기에 맞춰 간결하게 제시한다.

- **독자와 얻을 것:** 추정이면 추정이라고 표시.
- **우선 고칠 부분:** 원문 근거, 독자 영향, 수정 예시. 중복 지적은 묶는다.
- **수정안:** 요청에 따라 핵심 구간 또는 전체 글. 리뷰만 요청했다면 파일을 덮어쓰지 않는다.
- **보존·확인 사항:** 유지한 조건과 사실, 추가 확인할 정보, 화면 검수 여부.

초안 비교를 요청받으면 같은 독자와 목적을 기준으로 양쪽의 구체적인 문장을 비교한다. 길이나 유창함만으로 승자를 정하지 않는다. 더 나은 이유와 잃는 것을 설명하고 근거가 부족하면 동등 또는 판단 유보로 둔다. 점수표와 외부 평가 도구는 기본으로 요구하지 않는다.

## 근거와 적용 범위

Jev 연동이나 판정 모델 실험을 요청하면 [Jev 비교 설계](references/jev-comparison.md)를 읽는다. 이 문서는 구현 설계이며 실행 스크립트나 API 연결은 아직 포함하지 않는다. 일반 검수에는 필요 없다.

사용자가 제공한 GeekNews 한국어 정리와 Michael Lynch의 [Anti-Patterns in Software Blogging](https://refactoringenglish.com/blog/anti-patterns-software-blogging/)을 바탕으로 만든 검수 지침이다. 원문 전체의 복제·번역이 아니라 실무용 재구성과 자체 예시다. 참고 글을 매번 다시 열 필요는 없다.

증상·환경·해결 변경 보존은 사용자가 제공한 [GeekNews 토론](https://news.hada.io/topic?id=34962)의 geulway 댓글에서 가져온 보완 관점이다. 정보 보존 절차, 출력 형식, 초안 비교 방식은 이 스킬의 운영 규칙이며 원저자의 주장으로 인용하지 않는다.
