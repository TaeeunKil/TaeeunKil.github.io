하드웨어 기반 SSH 적용기를 읽고

2026.11.11SSH / Security / 학습 노트

개인키가 하드웨어 안에 있으면 SSH는 어떻게 인증할까. YubiKey와 TPM, Secure Enclave의 동작과 키 사용 조건을 찾아봤다.

GeekNews에서 「내 SSH 키를 모두 삭제했다」라는 글을 봤다. 제목을 보고 키를 지우면 서버에는 어떻게 접속한다는 건지 궁금했다. 원문의 저자 Alex Haydock은 파일로 보관하던 SSH 개인키를 YubiKey와 TPM, Apple Secure Enclave에 묶인 키로 옮겼다.

개인키를 하드웨어 안에 두고도 인증할 수 있다는 게 궁금해서 SSH 인증 과정부터 찾아봤다. 아직 내 환경에 적용해보지는 않았다. 원문에서 소개한 방법과 관련 문서를 읽으며 이해한 내용을 정리한 글이다.

SSH는 원래 개인키를 서버로 보내지 않는다

먼저 이해해야 할 부분은 공개키 인증에서 개인키가 하는 일이었다. 서버에 등록하는 것은 공개키다. 클라이언트는 대응하는 개인키로 인증 요청에 서명하고 서버는 공개키로 그 서명이 유효한지 확인한다. 개인키 자체를 서버에 전달할 필요가 없다.

여기서 서명은 인증 요청에 대한 암호학적 증명이다. SSH 인증 표준에 따르면 서명 대상에는 현재 연결의 세션 식별자와 사용자 이름 등을 포함한 인증 요청 데이터가 들어간다. 그래서 한 번 만든 서명을 복사해 다른 연결에서 그대로 재사용하는 식으로 인증할 수 없다.

이 구조라면 개인키를 보관한 장치에 서명을 요청하고 결과만 받아와도 된다. SSH 클라이언트가 개인키의 실제 값을 직접 읽을 필요는 없다. 파일 기반 키에서는 소프트웨어가 맡던 개인키 연산을 하드웨어에 요청하는 방식이다.

YubiKey는 인증에 필요한 서명을 만든다

YubiKey는 Yubico가 만드는 보안키 제품군이다. 웹사이트 로그인에도 쓰이지만 FIDO를 지원하는 OpenSSH와 호환되는 장치에서는 SSH 인증에도 쓸 수 있다. OpenSSH의 ed25519-sk나 ecdsa-sk에서 sk는 Security Key를 뜻한다. 장치가 지원하는 알고리즘에 따라 사용할 키 종류가 달라진다.

YubiKey를 사용하는 공개키 인증을 단순화하면 다음과 같다.

  1. SSH 클라이언트가 서버와 연결하고 서버의 신원을 확인한다.
  2. 클라이언트가 현재 연결의 사용자 인증에 필요한 서명 데이터를 준비한다.
  3. 클라이언트가 YubiKey에 서명을 요청한다. 설정에 따라 사용자가 보안키를 터치하거나 PIN으로 본인을 확인한다.
  4. YubiKey가 개인키로 서명하고 결과를 클라이언트에 돌려준다.
  5. 클라이언트가 서명을 포함한 인증 요청을 보내면 서버가 등록된 공개키와 정책으로 확인한다.

원문에서 사용하는 resident 키는 디스크에도 파일이 생긴다. 이 파일은 해당 키를 사용하기 위한 핸들이다. 파일을 복사해도 대응하는 YubiKey가 없으면 서명할 수 없다. 클라이언트나 에이전트는 개인키 대신 이 핸들을 이용해 장치에 작업을 요청한다. Yubico의 SSH 안내에서도 이 차이를 설명한다.

보안키가 SSH 연결의 모든 데이터를 암호화하는 것은 아니다. 이 설명에서 보안키가 맡는 일은 사용자 인증용 서명이다. 서버의 신원을 확인하는 호스트 키와 접속 후 통신을 보호하는 암호화 과정은 구분해서 봐야 한다.

resident는 새 컴퓨터에서 핸들을 복구할 수 있다는 뜻이다

처음에는 하드웨어로 보호하는 키를 모두 resident라고 생각하기 쉬웠다. OpenSSH의 -O resident는 인증에 필요한 키 핸들을 보안키 자체에도 저장하는 옵션이다. 다른 컴퓨터에서 보안키를 연결하고 ssh-keygen -K를 실행하면 그 핸들을 가져올 수 있다. 개인키를 평문으로 꺼내오는 명령은 아니다.

non-resident 키는 로컬 핸들 파일도 필요하다. 따라서 보안키가 있어도 파일을 잃어버리면 해당 키를 사용하지 못할 수 있다. resident 키는 이동이 편한 대신 장치를 잃어버렸을 때 그 안의 자격증명이 사용되지 않도록 사용자 확인 설정을 함께 생각해야 한다.

터치는 사람이 장치에 접촉했다는 존재 확인이고 PIN이나 생체인증은 사용자 확인에 해당한다. verify-required는 사용자 확인을 요구하는 옵션이다. resident 자체가 매번 PIN을 요구한다는 뜻은 아니다. 각 옵션의 의미는 OpenSSH 매뉴얼의 FIDO 설명에서 확인할 수 있다.

TPM과 Secure Enclave는 컴퓨터에 붙어 있다

원문은 별도 보안키 외에도 PC의 TPM과 Mac의 Secure Enclave를 활용한다. 하드웨어가 개인키를 보호한다는 공통점은 있지만 다른 컴퓨터로 옮겨 쓸 수 있는지는 다르다.

방식키를 사용하는 데 필요한 것장치를 바꾸면
FIDO 보안키해당 보안키와 필요한 핸들보안키를 옮겨 사용. non-resident 키는 핸들 파일도 필요
TPM키를 생성한 TPM과 해당 키 파일이 글에서 다루는 키는 다른 PC로 파일만 옮겨 쓸 수 없음
Secure Enclave키가 만들어진 Mac내보낼 수 없는 키는 새 Mac에서 다시 만들고 등록해야 함

ssh-tpm-agent는 TPM을 사용하는 SSH 에이전트다. TPM에서 만든 키의 암호화된 데이터가 .tpm 파일로 디스크에 남고 원래 TPM에 묶여 있어 다른 PC에 복사하는 것만으로는 쓸 수 없다. 기반 라이브러리의 서명 구현도 TPM을 통해 개인키 연산을 수행한다. 암호화된 키 파일이 디스크에 있다는 설명을 개인키를 평문으로 꺼내 일반 프로그램에서 사용한다는 뜻으로 읽으면 안 된다.

다만 원문에서 설명하는 구성은 TPM의 PCR 값을 확인하지 않는다. PCR은 부팅 상태를 측정한 값을 보관하는 레지스터다. 같은 TPM이 필요하다는 조건에 더해 특정 부팅 상태에서만 키를 쓰도록 제한하는 구성까지 갖춘 것으로 이해해서는 안 된다.

Mac 쪽에서는 sc_auth로 Secure Enclave가 보호하는 키를 만들고 SSH에서 그 키를 사용하도록 연결한다. sc_auth 매뉴얼의 p-256-ne는 내보낼 수 없는 키를 지정하고 bio는 생체인증 보호를 지정한다. 저자는 Touch ID를 요구하는 키를 만들려다 덮개가 닫힌 상태에서는 실패했다고 적었다. 책상에서 MacBook을 닫아두고 쓰는 사람이라면 이런 사용 조건도 확인해야겠다.

키를 복사하지 못해도 사용을 시도할 수는 있다

하드웨어 키의 이점을 이해하면서 같이 봐야 했던 부분이다. 악성 프로그램이 키 파일을 가져가 자기 컴퓨터에서 사용하는 공격은 어려워진다. 하지만 보안키가 꽂혀 있는 PC가 이미 침해됐다면 공격자가 그 장치에 서명을 요청할 수 있는지는 별도 문제다.

원문은 무인 작업을 위해 no-touch-required를 사용하는 경우도 다룬다. 터치를 생략하면 사용자는 자리에 없어도 되고 공격자도 사람의 개입 없이 키 사용을 시도할 수 있다. 이 설정은 서버 쪽에서도 허용해야 한다. 반대로 터치를 유지하더라도 사용자가 승인하는 요청이 자신이 의도한 것인지 보안키만으로 판단해주지는 않는다. 이미 열린 SSH 세션에서 실행되는 명령을 하나씩 승인하는 기능도 아니다.

그래서 개인 접속과 자동 배포는 필요한 조건이 다르다. 자동 작업에 사람이 매번 터치할 수는 없다. 자동화용 키에는 접속 대상과 권한을 제한하는 설계가 함께 필요하고 개인용 키는 사용자가 개입하는 흐름을 유지할 수 있다.

적용한다면 예비 접속부터 준비해야겠다

원문 저자도 암호문구를 설정한 기존 SSH 키가 대부분의 위협 모델에서 충분할 수 있다고 적었다. 파일이 유출되더라도 암호문구가 추가 방어가 된다. 하드웨어 키로 옮기는 이유는 그런 키를 복사해 가져가는 공격을 더 어렵게 만들고 싶은지에 따라 달라진다.

내가 적용한다면 기존 키를 남겨둔 상태에서 새 키를 추가하고 실제 접속부터 확인할 것 같다. 예비 보안키에는 별도의 키를 생성해 공개키를 함께 등록하고 주 장치 없이도 들어갈 수 있는지 시험해야 한다. 같은 보안키를 다시 꽂아 접속되는지만 확인해서는 분실했을 때의 복구 경로를 검증할 수 없다.

새 접속과 복구 경로가 확인된 뒤에는 기존 공개키의 접근 권한도 회수해야 한다. 로컬 개인키만 지우고 서버에 기존 공개키를 남겨두면 다른 곳에 복사돼 있던 개인키로는 계속 접속할 수 있다.

처음 궁금했던 개인키 없이 어떻게 인증하느냐는 질문은 서명을 어디에서 만드느냐로 이어졌다. SSH 클라이언트가 하드웨어에 서명을 요청할 수 있으니 키를 직접 읽지 않아도 인증할 수 있었다. 실제로 써본다면 PIN과 터치가 Git 작업 중 얼마나 자주 필요한지부터 확인해보고 싶다.
