REA란? 코딩 에이전트로 프로그램 내부를 분석하는 방법

2026.10.15REA · Reverse Engineering · AI · 학습 노트

역공학의 기본 개념부터 REA와 분석 도구의 역할, 실제 사례와 검증 방법까지 정리했다.

REA는 코딩 에이전트가 프로그램 내부를 조사할 수 있게 해주는 역공학 도구다. 실행 파일이나 앱 패키지를 대상으로 코드를 읽고, 함수 사이의 관계를 따라가며 특정 기능의 동작을 설명하는 데 사용한다.

예를 들어 “이 게임은 탄환을 어떻게 플레이어 쪽으로 발사하는가?”라는 질문을 받으면, 답을 찾으려면 관련 코드를 찾아 입력값과 연산을 확인해야 한다. REA는 이 조사에 필요한 도구와 결과를 에이전트에 제공한다. 에이전트는 반환된 명령어와 참조 정보를 해석해 다음 조사 대상을 정한다.

이 글은 공식 문서와 공개 사례를 바탕으로 REA의 역할과 분석 과정을 정리한 학습 노트다. 사례의 수치와 검증 결과는 각 프로젝트의 공개 기록에 따른다.

역공학은 무엇을 알아내는 작업인가

소프트웨어 개발에서는 소스 코드를 실행 가능한 프로그램으로 만든다. 역공학은 완성된 프로그램을 조사해 내부 구조와 동작을 알아내는 작업이다. 소스가 없는 실행 파일에서 계산 규칙을 찾거나, 배포된 앱 패키지에서 버튼을 누른 뒤 어떤 처리가 이어지는지 추적하는 일이 여기에 해당한다.

실행 파일에는 원래 변수 이름이나 주석이 남아 있지 않을 수 있다. 컴파일 과정에서 함수가 합쳐지거나 코드 순서가 달라지기도 한다. 따라서 기계어를 읽기 쉬운 코드로 표현하는 디컴파일 결과가 원본 소스와 같다고 볼 수는 없다.

함께 등장하는 용어도 구분해두면 사례를 읽기 쉽다.

  • 명령어: 프로세서가 수행하는 연산을 표현한 것. 값을 읽고 더하거나 조건에 따라 다른 위치로 이동하는 동작을 확인한다.
  • 의사코드: 동작을 읽기 쉬운 코드 형태로 표현한 것. 분석 도구가 추정한 타입이나 이름이 포함될 수 있다.
  • 참조와 호출 관계: 어떤 코드가 특정 데이터에 접근하고 어떤 함수가 다른 함수를 부르는지 나타내는 정보다.
  • 정적 분석: 프로그램을 실행하지 않고 파일과 코드를 조사하는 방식이다.
  • 동적 분석: 프로그램을 실행하면서 값의 변화나 실제 호출을 관찰하는 방식이다.

에이전트와 REA, 분석 도구는 역할이 다르다

네이티브 실행 파일을 조사하는 경우 REA는 Ghidra, Hopper, IDA 같은 분석 도구와 연결된다. 사용자는 에이전트에 대상 파일과 질문을 주고, 에이전트는 REA가 제공하는 도구로 필요한 정보를 조회한다. 설치와 지원 조건은 공식 시작 안내에서 확인할 수 있다.

구성분석에서 하는 일
사용자대상 프로그램과 알아내려는 동작을 정한다.
코딩 에이전트조사할 위치를 선택하고 반환된 결과를 해석한다.
REA프로그램 조사 도구를 제공하고 코드와 참조 정보를 반환한다.
분석 백엔드대상 형식에 맞춰 명령어, 디컴파일 결과 등의 분석 정보를 제공한다.

필요한 백엔드는 대상에 따라 달라진다. JavaScript 앱의 소스를 읽는 작업과 네이티브 실행 파일의 기계어를 조사하는 작업은 같은 과정이 아니다. Android APK도 별도의 분석 구성이 필요하다. REA를 설치했다는 사실만으로 모든 형식의 분석 환경이 준비되는 것은 아니다.

분석은 질문을 좁히고 근거를 따라가는 과정이다

“게임 전체를 분석해줘”보다 “탄환의 발사 각도를 계산하는 규칙을 찾아줘”처럼 기능 하나를 지정하면 조사 범위가 분명해진다. 이후에는 다음 흐름을 반복한다.

  1. 대상을 확인한다. 파일 형식과 버전을 확인해 어떤 프로그램을 분석하는지 고정한다.
  2. 관련 코드를 찾는다. 문자열, 함수, 클래스 등에서 기능과 연결되는 단서를 찾는다.
  3. 입력과 호출을 추적한다. 값이 어디에서 들어와 어떤 조건과 계산을 거치는지 확인한다.
  4. 규칙을 설명한다. 확인한 연산을 계산식이나 읽기 쉬운 코드로 표현한다.
  5. 결과를 검증한다. 원본 동작, 추출한 코드 또는 공개 테스트와 비교한다.

아래 세 사례는 이 흐름이 서로 다른 프로그램에 적용되는 모습을 보여준다. 게임에서는 명령어와 좌표 계산을 읽고, 인증 앱에서는 클래스와 메서드의 호출을 따라간다.

동방환상향의 탄막이 플레이어를 조준하는 방법

동방환상향(Touhou 4: Lotus Land Story, TH04)은 PC-98용 슈팅 게임이다. REA의 TH04 사례에서는 원본 DOS 실행 파일을 읽어 원형 탄막의 발사 각도를 조사했다. 질문은 “원을 이루는 총알들이 어떻게 플레이어 쪽으로 방향을 맞추는가?”다.

이 게임은 한 바퀴를 256단위로 표현한다. 탄환이 16개라면 방향을 16단위씩 떨어뜨려 배치하고, 여기에 플레이어를 향하는 각도를 더하면 원형 탄막 전체가 회전한다. 그림에서는 그 차이를 볼 수 있다.

REA는 각도 계산 함수의 명령어와 참조 정보를 반환했다. 탄환 번호를 256배 한 뒤 개수로 나누는 연산, 플레이어와 발사 지점의 좌표 차이로 방향을 구하는 호출을 확인할 수 있었다. 공개된 C++와 대조하면서 각 명령이 탄막 계산의 어느 부분인지 설명한다.

검증 결과는 기존 TH04 복원 프로젝트의 기록과 구분해서 읽어야 한다. 탄환 생성 코드 2,139바이트의 컴파일 일치 검사는 그 프로젝트에서 수행했고, REA 사례는 같은 원본을 새로 조사한 내용이다. REA가 혼자 게임 전체를 복원했다는 사례는 아니다.

DX-Ball에서 벽돌 위치가 소리 방향이 되기까지

벽돌 깨기 게임 DX-Ball에서는 공이 벽돌에 부딪힌 위치에 따라 소리가 좌우로 배분된다. DX-Ball 1.07 분석 사례는 이 계산을 실행 파일에서 찾아 C 함수로 표현한 과정이다.

처음 디컴파일한 결과에는 숫자 변환 함수 호출만 나타났다. 디컴파일은 기계어를 사람이 읽기 쉬운 코드 형태로 바꾸는 작업인데, 이 결과만으로는 계산 과정이 드러나지 않았다. 에이전트는 REA로 실제 명령어와 호출하는 함수를 확인해 입력이 화면의 가로 좌표임을 알아냈고, 실행 파일에서 연산에 쓰인 상수도 읽었다.

찾아낸 규칙은 가로 좌표에 1.5625를 곱하고 500을 뺀 뒤 배율을 적용하는 것이다. 배율이 1이면 화면 왼쪽의 좌표 0은 −500, 가운데 320은 0, 오른쪽 640은 500이 된다.

공식 기록에 따르면 복원 함수는 원본과 3,205개 입력을 비교했고, 지정한 컴파일 환경에서는 함수의 63바이트도 일치했다. 다만 이 결과는 해당 함수의 검증이다. 플레이 가능한 게임 전체의 복원은 여전히 진행 중이다.

인증 앱의 여섯 자리 코드를 재현하기

게임 외의 사례로는 Aegis Authenticator 분석이 있다. 대상은 배포된 Android APK 3.4.3이고, 조사한 기능은 시간에 따라 바뀌는 일회용 인증 코드다.

REA로 APK의 클래스 3,077개 중 관련 후보를 찾고, 코드 생성 함수가 화면 표시와 복사 기능에서 호출되는 경로를 추적했다. 이어 시간 간격과 자릿수의 기본값, 계정 키를 사용하는 계산을 읽었다. 기본 설정에서는 시간을 30초 구간으로 나누므로 같은 키라면 한 구간 안에서는 같은 코드가 나온다.

분석 결과로 만든 브라우저 데모에서는 시계를 직접 바꿀 수 있다. 공개 테스트 키를 사용하는 예시에서 59초의 코드는 287082, 60초의 코드는 359152다. 공식 사례 페이지의 데모에서 시간 경계를 넘길 때 결과가 바뀌는 모습을 확인할 수 있다.

공식 설명은 추출한 Java 메서드와 별도 재현 구현을 133개 사례로 비교했다고 밝힌다. APK를 정적으로 분석하고 추출 코드를 테스트한 결과이며, 다른 사람의 인증 키를 알아내거나 로그인을 우회한 사례는 아니다.

분석 결과에서 확인해야 할 것

REA가 반환한 코드, 에이전트의 해석, 별도로 수행한 검증은 구분해서 읽어야 한다. 반환된 명령어는 분석 근거이고, “이 값은 플레이어의 방향이다”라는 설명은 주변 코드와 함께 확인할 해석이다. 재구현한 함수가 원본과 같은 결과를 내는지는 비교 실행으로 확인한다.

검증 수치에도 범위가 있다. DX-Ball의 함수가 여러 입력에서 일치했다는 결과는 그 함수의 동작을 뒷받침한다. TH04의 컴파일 일치 기록은 지정한 코드 구간과 빌드 조건에 대한 결과다. 이를 게임 전체가 완전히 복원됐거나 모든 환경에서 같은 동작을 보장한다는 의미로 넓힐 수는 없다.

공식 사례를 읽을 때는 대상 파일과 버전, REA가 반환한 근거, 에이전트가 구성한 설명, 실제 검증 방법을 함께 확인하면 된다. 같은 기능처럼 보여도 배포 버전이 바뀌면 코드와 주소가 달라질 수 있으므로 분석 결과가 어떤 파일을 대상으로 하는지도 남겨야 한다.
