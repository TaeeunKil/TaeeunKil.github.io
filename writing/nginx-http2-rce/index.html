NGINX HTTP/2 취약점 - CVE-2026-123007, CVE-2026-123633

2026.11.19NGINX / HTTP/2 / Security

NGINX의 HTTP/2 취약점 두 건과 보안 업데이트, ingress-nginx 마이그레이션, HTTP/2 비활성화 방법을 정리했다.

NGINX가 HTTP/2 요청을 처리하는 과정에서 인증 없이 원격 코드 실행으로 이어질 수 있는 취약점 두 건이 공개됐다. 영향을 받는지 판단하려면 실제로 요청을 처리하는 NGINX의 버전과 HTTP/2 설정부터 확인해야 한다. NGINX 공식 보안 공지

어떤 환경이 영향을 받나

CVE-2026-123633은 NGINX가 HTTP/2 요청을 백엔드로 프록시하는 과정에서 이미 해제된 메모리에 접근할 수 있는 문제다. CVE-2026-123007은 HTTP/2 흐름 제어 과정에서 메모리가 손상될 수 있는 문제다. Wiz는 두 번째 취약점의 경우 백엔드 없이 정적 파일만 제공하는 구성에서도 원격 코드 실행이 가능하다는 점을 확인했다. Wiz 분석

CDN을 사용하면 브라우저에서 CDN까지의 연결과 CDN에서 원본 서버까지의 연결이 따로 맺어진다. 브라우저 개발자 도구에 h2가 표시돼도 원본 NGINX는 HTTP/1.1로 요청을 받을 수 있다. 원본의 실행 설정을 보고, 직접 접근할 수 있는 환경에서 원본과의 TLS 연결이 h2로 협상되는지 확인한다. Cloudflare 원본 연결 문서

1. 보안 패치가 반영된 버전으로 업데이트

NGINX OSS는 stable 1.30.7과 mainline 1.31.9부터 두 취약점의 수정 사항이 들어갔다. 배포판 패키지나 컨트롤러 이미지로 운영한다면 해당 배포처의 보안 공지에서 두 CVE가 수정된 버전을 확인한다. 업데이트 후에는 실제로 요청을 처리하는 인스턴스에 새 버전이 반영됐는지 확인한다. NGINX 릴리스 공지

제가 기존에 운영하던 Kubernetes 환경에서는 커뮤니티 ingress-nginx를 사용하고 있었다. 이 프로젝트는 2026년 3월에 지원이 종료됐다. NGINX가 컨트롤러 이미지에 포함돼 있으므로 보안 업데이트를 계속 받으려면 유지보수 중인 Ingress 또는 Gateway 컨트롤러로 마이그레이션해야 한다. Kubernetes 지원 종료 공지

ingress-nginx에서 다른 컨트롤러로 옮기는 순서

기존 Kubernetes Ingress 리소스를 활용하고 싶다면 F5 NGINX Ingress Controller가 교체 후보가 될 수 있다. OSS 5.8.0에는 두 CVE를 수정한 NGINX 1.31.9가 포함돼 있다. 컨트롤러마다 리소스와 설정을 해석하는 방식이 다르므로 다음 순서로 옮긴다. F5 릴리스 노트

  1. 기존 트래픽 경로와 설정을 목록으로 만든다. Ingress별 호스트와 경로, 백엔드 Service, TLS Secret, IngressClass, 애노테이션을 확인한다. 컨트롤러의 ConfigMap과 로드밸런서, DNS 또는 CDN의 원본 주소도 함께 기록한다.
  2. 새 컨트롤러를 병행 배포한다. 별도 IngressClass와 테스트용 엔드포인트를 만들고, 검증할 Ingress 복사본을 새 클래스에 연결한다. 호스트 포트를 쓰는 환경이라면 기존 컨트롤러와 포트가 충돌하지 않도록 서비스나 노드를 분리한다. 컨트롤러 병행 운영 문서
  3. 컨트롤러별 설정을 옮기고 동작을 비교한다. 경로 재작성, IP 허용 목록, 요청 크기 제한과 타임아웃처럼 기존 애노테이션에 담긴 설정을 새 컨트롤러의 애노테이션이나 정책으로 옮긴다. 같은 호스트를 여러 Ingress가 나눠 쓰는 경우에는 새 컨트롤러가 경로를 어떻게 합치는지 확인한다. 테스트 엔드포인트에서 인증서, 리디렉션, 로그인, 파일 업로드, WebSocket, 접근 제한 중 실제 사용하는 기능을 검증한다. 마이그레이션 가이드
  4. 트래픽을 전환하고 되돌릴 경로를 확보한다. 검증을 마친 뒤 로드밸런서, DNS 또는 CDN 원본을 새 컨트롤러 쪽으로 전환한다. 전환 직후 오류율과 주요 서비스 응답을 확인하고, 이상이 생기면 기존 엔드포인트로 복귀할 수 있도록 기존 컨트롤러를 검증이 끝날 때까지 유지한다.

2. 업데이트 전까지 HTTP/2 끄기

패치 적용이나 컨트롤러 교체에 시간이 필요하면 HTTP/2를 비활성화해 이번 두 취약점을 완화할 수 있다.

  • NGINX를 직접 운영한다면 listen 지시어에서 http2 옵션을 제거한다. NGINX 1.25.1 이상에서는 대상 서버 블록에 http2 off;를 설정해 상위 설정에서 HTTP/2를 활성화한 경우도 끈다. NGINX HTTP/2 설정 문서
  • 커뮤니티 ingress-nginx에서는 컨트롤러가 참조하는 ConfigMap의 data에 use-http2: "false"를 지정한다. ingress-nginx 설정 문서

적용 전에는 gRPC처럼 HTTP/2를 전제로 하는 서비스가 있는지 확인한다. 적용 후에는 원본에서 h2가 더 이상 협상되지 않는지 확인하고, 주요 웹과 API 요청이 HTTP/1.1로 정상 처리되는지 점검한다.
