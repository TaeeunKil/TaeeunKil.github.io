BM25와 grep으로 FRAMES 91%를 기록한 에이전틱 RAG

2026.11.03AI / Agent / RAG / Information Retrieval / 학습 노트

RAGFlow가 보고한 FRAMES 91%와 BrowseComp-Plus 85%의 조건 그리고 주장-근거 트리의 토큰 절감과 지연 시간 변화를 정리했다.

RAGFlow 연구진의 논문을 읽고

2026년 10월 30일 공개된 논문 v1을 바탕으로 썼다. 수치는 저자들이 보고한 실험 결과다. 직접 재현한 값은 아니다. 논문 원문[1]

벡터 검색 없이 BM25와 grep만으로 에이전틱 RAG가 BrowseComp-Plus에서 85%를 기록했다. FRAMES 점수는 91%였다. RAGFlow 연구진이 MiniMax M3를 답변 모델로 사용한 실험 결과다. 두 벤치마크는 과제와 평가 조건이 달라 점수를 직접 비교할 수 없다.

에이전틱 RAG에서는 에이전트가 검색어를 만들고 결과를 읽는다. 부족한 정보가 있으면 검색어를 고쳐 다시 찾는다. 답에 필요한 근거가 모였는지도 스스로 판단한다. 검색을 한 번 호출하는 대신 이런 검색과 읽기를 반복한다.

그래서 “인덱스가 하나도 없다”는 설명은 정확하지 않다. 이 실험은 BM25와 grep으로 어휘 검색을 했다. 쓰지 않은 것은 벡터 검색과 미리 만들어둔 요약 트리나 그래프 같은 지식 구조다.

정확도는 높았지만 구조가 더 높이진 않았다

비교의 기준이 된 BM25와 grep 구성은 FRAMES에서 91%를 기록했다. BrowseComp-Plus에서는 85%였다. 두 벤치마크는 질문 유형과 평가 조건이 달라 점수를 나란히 비교할 수 없다. 답변 모델은 MiniMax M3였다.

FRAMES에서 연구진은 요약 트리와 문서 목차형 구조를 시험했다. LLM 위키와 엔티티 관계 그래프도 붙였다. 단일 실행에서 어느 구조도 기준 구성보다 정확도가 나아졌다고 확인할 만한 변화는 없었다. 목차형 구조는 작은 문서 묶음에서는 차이가 없었지만 FRAMES 규모에서는 점수를 낮췄다. 각 구조를 한 번씩 실행했으므로 작은 차이까지 없다고 입증한 실험은 아니다.

논문에서 확인한 눈에 띄는 개선은 정확도가 아니라 토큰과 지연 시간이다. 그래프가 여러 출처를 연결하거나 온톨로지가 용어를 관리하는 효과는 별도 평가가 필요하다. 연구진은 배포 환경에서의 이점도 제안하지만 벤치마크 점수로 확인한 것은 아니다.

저자들은 dense retrieval을 더한 자신들의 실험에서는 정확도가 낮아졌다고 적는다. 그러나 논문에 보고한 벤치마크 평가에는 dense retrieval 조건이 없다. 따라서 이 결과는 해당 에이전트 구성이 벡터 검색 없이 높은 점수를 낸 사례다. 모든 문서와 질문에서 벡터 검색이 불필요하다는 증거는 아니다.

정확도 개선은 보이지 않았고 읽는 양은 줄었다

주장-근거 트리도 FRAMES 정확도에서 기준 구성보다 나아졌다고 판별할 만한 결과를 내지 못했다. 줄어든 것은 모델이 읽는 양이었다. 문서를 읽은 모델이 짧은 주장과 이를 뒷받침하는 원문 문장을 짝지어 둔다. 근거 문장은 원문 그대로 보존하고 문서 안의 위치도 기록한다. 원문에서 해당 문장을 찾지 못하면 그 쌍은 버린다.

질문이 들어오면 검색 방식은 그대로 둔다. BM25와 grep으로 문서를 찾은 뒤 해당 문서의 주장-근거 쌍을 먼저 모델에 보여준다. 그 정보만으로 답하기 어렵다면 원문을 열어 읽는다. 트리의 내부 노드는 탐색을 돕고 잎에는 주장과 확인 가능한 원문 근거를 둔다.

FRAMES 200개 질문에서 게이트가 근거를 충분하다고 판단한 경우 전체 토큰은 91% 줄었다. 충분하지 않은 경우에는 원문을 다시 읽는 비용까지 붙어 1.9% 늘었다. 둘을 합친 평균 감소 폭은 38%였다. 여기에는 검색 호출과 도구 결과와 원문 읽기 그리고 답변 생성에 쓴 토큰이 모두 들어간다.

140초에서 30초로 줄었지만 질문은 7개였다

판단 게이트는 질문과 먼저 가져온 근거를 살펴 원문을 더 읽을지 정한다. 연구진은 주장-근거 트리에 게이트를 더한 구성에서 평균 응답 시간이 140초에서 30초로 줄었다고 보고했다.

이 시간 비교는 두 구성에서 모두 답한 질문 7개로 계산했다. 주장-근거 쌍만 적용한 별도 비교에서는 토큰이 절반가량 줄었지만 응답 시간은 약 세 배 늘었다. 작은 근거 묶음으로는 답을 완성하려고 검색을 더 반복했기 때문이다. 토큰을 덜 쓴다고 응답까지 빨라지는 것은 아니다. 38% 토큰 감소와 140초에서 30초라는 결과도 같은 실험 수치로 묶어 읽으면 안 된다.

결과를 다른 문서에 옮길 때 볼 점

BrowseComp-Plus 질문 하나에 사용한 토큰은 약 300만 개였다. 이 벤치마크는 기준 검색 하네스의 규모 확인에 쓰였고 주장-근거 트리의 토큰 절감 효과를 재는 데는 쓰이지 않았다. FRAMES는 영어 위키백과 문서로 만든 벤치마크다. 표와 스캔 파일이 많거나 전문 용어가 쓰이는 사내 문서에서 같은 결과가 난다고 단정하기 어렵다.

FRAMES의 전체 정확도와 토큰 집계에는 200개 질문이 들어갔다. 논문은 신뢰구간과 반복 시드 결과를 제시하지 않는다. 구조별 정확도 비교는 한 번씩 실행했다. 특히 지연 시간 비교는 두 구성에서 답을 얻은 7개 질문만으로 계산했다.

게이트가 근거를 받아들였다는 사실은 그 근거가 실제로 충분하다는 보증도 아니다. 논문은 받아들인 근거를 사람이 따로 확인하는 감사를 제안한다. 하지만 게이트가 부족한 근거를 통과시킨 비율은 측정하지 않았다.

내 문서에서 벡터 검색이 필요한지는 같은 질문과 같은 답변 모델로 직접 비교해야 한다. 정확도와 토큰 수를 함께 재고 검색 횟수와 응답 시간도 기록할 필요가 있다. 이 논문의 결과는 그 비교를 시작할 때 참고할 기준선이다.
