주소창에 URL을 입력하면 화면은 어떻게 그려질까

2026.10.29Browser · Network · TLS · Web

URL 해석과 DNS, 연결 설정, TLS 인증서 검증, HTTP 응답, 브라우저 렌더링까지의 흐름을 따라간다.

주소창에 URL을 입력하면 브라우저는 목적지를 찾고 서버와 연결한 뒤 응답을 화면으로 바꾼다. HTTPS라면 HTTP 요청을 보내기 전에 TLS 핸드셰이크에서 서버 인증서도 확인한다.

이 과정은 한 줄로 정해진 고정 절차가 아니다. 브라우저 캐시나 기존 연결을 재사용하면 DNS 조회와 연결 설정을 건너뛸 수 있다. 서비스 워커가 요청을 처리할 수도 있다. 아래 흐름은 새 HTTPS 연결을 만들고 HTML을 처음 받는 경우를 중심으로 본다.

URL에서 목적지 정보를 읽는다

브라우저는 URL을 해석해 https 같은 스킴, 호스트명, 포트, 경로를 구분한다. 브라우저 정책이나 저장된 HSTS 규칙에 따라 HTTP 주소를 HTTPS로 바꿔 접속할 수도 있다. URL에 도메인 이름이 있다고 해서 매번 처음부터 DNS를 조회하는 것은 아니다. 브라우저와 운영체제의 캐시, 연결 재사용 여부가 영향을 준다.

새 주소를 찾아야 하면 브라우저는 운영체제의 이름 해석 기능에 요청한다. 이때 hosts 파일이나 로컬 캐시에서 답을 찾을 수도 있다. 답이 없으면 설정된 재귀 DNS 리졸버가 캐시를 확인하고, 필요할 때 루트 DNS, 최상위 도메인 DNS, 권한 DNS 서버를 차례로 찾아 IP 주소를 얻는다. 모든 페이지 요청이 매번 이 서버들을 순서대로 방문하는 것은 아니다.

서버와 연결하고 인증서를 확인한다

브라우저와 서버가 사용할 전송 방식에 따라 연결 과정이 달라진다. HTTP/1.1과 HTTP/2는 보통 TCP 연결 위에서 TLS를 협상한다. HTTP/3은 QUIC을 사용하며 TLS 1.3 핸드셰이크 메시지가 QUIC 연결 과정에 통합된다. 그래서 HTTP/3을 설명할 때는 “TCP 다음에 TLS”라고 뭉뚱그리지 않는 편이 정확하다.

TLS 1.3의 새 연결을 예로 들면 브라우저는 ClientHello에 지원 옵션과 서버 이름, 키 교환용 key_share 등을 담아 보낸다. 서버는 선택한 설정과 자신의 key_share를 돌려준다. 양쪽은 이 임시 키 교환 결과로 공유 비밀을 만들고, 핸드셰이크에 사용할 키를 파생한다.

이어 서버는 인증서 체인과 CertificateVerify 서명을 보낸다. 브라우저는 인증서가 신뢰하는 CA까지 이어지는지, 인증서의 호스트명이 URL의 호스트와 맞는지, 유효기간과 용도가 맞는지 확인한다. 인증서의 공개키로 CertificateVerify 서명도 검사한다. 이 서명은 서버가 인증서에 대응하는 개인키를 갖고 있으며 핸드셰이크 내용에 서명했다는 것을 증명한다.

인증서는 서버 신원을 확인하고 키 교환을 인증하는 데 쓰인다. 매 요청과 응답을 인증서의 공개키로 직접 암호화하는 방식은 아니다. 핸드셰이크가 성공하면 양쪽이 합의한 방향별 대칭 트래픽 키로 데이터를 보호한다. 이때 전송 내용은 기밀성과 무결성을 제공하는 AEAD 방식으로 암호화된다.

위 그림은 서버 인증서를 쓰는 새 연결의 기본 흐름이다. 세션 재개에서는 이전 연결에서 만든 PSK를 사용할 수 있어 인증서 메시지가 생략될 수 있다. 클라이언트 인증서를 요구하는 서비스나 0-RTT 데이터도 별도 조건과 절차가 있다. 자세한 메시지 정의는 TLS 1.3 표준과 QUIC에서 TLS를 사용하는 표준을 참고할 수 있다.

HTTP 응답을 받아 화면으로 바꾼다

핸드셰이크가 성공하면 브라우저가 HTTP 요청을 보낸다. 서버는 상태 코드와 헤더, HTML 본문을 돌려준다. 브라우저는 HTML을 읽는 동안 CSS, JavaScript, 이미지 같은 리소스를 발견하면 추가 요청을 보낸다. 기존 연결을 재사용하거나 여러 요청을 병렬로 처리할 수 있다.

HTML 파서는 문서를 DOM으로 만들고, CSS 파서는 스타일 규칙을 CSSOM으로 만든다. 브라우저는 표시할 요소와 계산된 스타일을 합쳐 렌더 트리를 만든 뒤 크기와 위치를 계산한다. 이후 픽셀을 그리고 필요하면 레이어를 합성해 화면에 표시한다. JavaScript가 DOM이나 스타일을 바꾸면 일부 단계를 다시 수행할 수 있다.

화면이 처음 나타났다고 모든 이미지와 스크립트가 다 도착한 것은 아니다. 브라우저는 첫 렌더링에 필요한 리소스를 기다리면서도 이후 콘텐츠를 계속 받아 페이지를 갱신한다. 리소스가 늦게 도착하거나 JavaScript가 화면 구조를 바꾸면 사용자가 본 화면도 다시 그려진다.

전체 흐름을 따라갈 때 기억할 점

  • 캐시나 기존 연결을 재사용하면 DNS, TCP, TLS의 일부 과정이 생략된다.
  • DNS 리졸버가 캐시를 갖고 있으면 루트부터 권한 DNS까지 전부 조회하지 않는다.
  • 인증서가 서버 신원을 증명하고, 임시 키 교환으로 만든 방향별 대칭 키가 실제 HTTP 데이터를 보호한다.
  • HTTP/3은 TCP 대신 QUIC을 사용하며 TLS 1.3과 함께 연결을 설정한다.
  • 브라우저는 문서 전체가 아니라 첫 화면에 필요한 리소스를 기준으로 렌더링을 시작할 수 있다.
