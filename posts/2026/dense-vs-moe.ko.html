모델 크기만으로 비교하기 어려웠다

기존에 사용하던 LLM 대신 더 큰 모델을 실행할 수 있는지 알아보다가 MoE를 공부하게 됐다. 모델 설명에는 전체 파라미터 수와 활성 파라미터 수가 따로 적혀 있었다. 모델은 큰데 실제 계산에는 일부만 참여한다는 설명이었다.

그러면 작은 모델처럼 실행할 수 있는 것인지, 쓰지 않는 나머지 파라미터는 왜 필요한지 궁금했다. 비교하려면 기존 Dense 모델에서 어떤 계산을 하는지부터 이해해야 했다.

여기서는 Transformer 기반 LLM의 Dense 구조와 일부 전문가만 선택하는 sparse MoE를 비교한다. 일반적인 MoE에는 모든 전문가의 출력을 사용하는 방식도 있지만 이후 MoE라는 이름은 sparse MoE를 가리킨다. NVIDIA의 구조 설명도 이 두 방식을 구분한다.

Dense에서는 같은 층의 FFN을 모든 토큰에 적용한다

LLM에 입력한 문장은 먼저 토큰으로 나뉜다. 토큰은 단어 전체일 수도 있고 단어의 일부나 기호일 수도 있다. 모델은 토큰을 숫자로 된 벡터로 바꾼 뒤 여러 층을 거치며 처리한다. 가중치는 학습으로 얻은 숫자들이고 이 벡터를 변환하는 연산에 사용된다.

Transformer의 한 층에서는 attention과 FFN(Feed-Forward Network)을 구분해볼 수 있다. attention은 다른 위치의 토큰 정보를 참고해 현재 표현을 만든다. FFN은 그렇게 얻은 각 위치의 벡터를 변환한다. 실제 층에는 정규화와 잔차 연결 등도 있지만 Dense와 MoE를 비교할 때 먼저 볼 부분은 FFN이다.

Dense 구조에서는 같은 층에 들어오는 토큰들이 같은 FFN 가중치를 사용한다. 입력 벡터가 다르므로 결과도 다르지만 토큰에 따라 FFN 블록을 골라 바꾸지는 않는다. 다음 층에는 그 층의 다른 가중치가 있고 이 흐름이 반복된다.

Attention Is All You Need의 3.3절은 같은 층의 FFN을 각 위치에 동일하게 적용하고 층 사이에는 다른 파라미터를 사용한다고 설명한다. 원논문은 encoder-decoder 구조지만 이 부분이 비교의 출발점이 됐다.

Dense를 “모든 숫자를 매번 예외 없이 전부 읽는 모델”로 외우는 것은 피하려 한다. 예를 들어 입력 임베딩은 토큰에 해당하는 벡터를 찾아오는 경로다. 여기서 말하는 차이는 주요 계산 블록을 공통으로 사용하느냐와 토큰에 따라 일부 전문가를 선택하느냐다.

MoE는 FFN 자리에 여러 전문가와 router를 둔다

일반적인 Transformer MoE는 Dense의 FFN을 여러 전문가(expert)와 router로 구성된 블록으로 바꾼다. expert는 입력 벡터를 받아 출력 벡터를 만드는 작은 신경망이다. 흔히 FFN으로 구성한다. attention을 포함한 모델 전체가 전문가 여러 개로 통째로 복제되는 것은 아니다.

router는 현재 토큰의 벡터를 보고 전문가별 점수를 계산한다. 그중 상위 몇 개를 선택해 계산을 맡기고 선택된 전문가의 출력에 가중치를 주어 합친다. router 역시 학습되는 모델의 일부다. 이 구성은 Hugging Face의 MoE 설명에서 살펴봤다.

전문가라는 이름 때문에 수학 챗봇과 번역 챗봇을 따로 만들어 질문을 넘기는 모습을 떠올리기 쉽다. 실제로는 모델 내부의 계산 블록을 토큰 단위로 선택한다. 한 질문을 전문가 한 명에게 맡겨 답변 전체를 작성하게 하는 방식과 다르다.

학습 중 특정 패턴을 더 많이 처리하는 전문가가 생길 수는 있다. 그렇다고 사람이 정한 분야 이름이 각 전문가에 미리 붙어 있는 것은 아니다. Hugging Face의 구현 설명도 expert를 분야별로 지정한 모듈로 이해하지 않도록 구분한다.

전문가 선택은 각 층에서 다시 일어난다

Mixtral 8x7B를 보면 구체적인 계산을 따라가기 쉽다. 각 층에 FFN 전문가가 8개 있고 토큰마다 router가 그중 2개를 선택한다. 같은 토큰도 다음 층에서는 그 층의 다른 전문가들을 거친다. Mixtral 논문의 구조 설명에 이 경로와 출력의 가중합이 나와 있다.

8개 중 2개라는 숫자는 Mixtral의 선택이다. 모든 MoE가 같은 수의 전문가를 사용하지는 않는다. Switch Transformer는 토큰당 전문가 하나만 고르는 top-1 routing을 사용한다.

전체 파라미터와 활성 파라미터는 다른 숫자다

전체 파라미터는 모델이 가진 가중치의 총량이다. 활성 파라미터는 한 토큰을 처리하는 경로에서 사용하는 가중치의 규모다. MoE에서는 선택되지 않은 전문가가 있어 두 숫자의 차이가 커질 수 있다.

한 MoE 블록에 같은 크기의 전문가 8개가 있고 각 전문가가 가중치 100개를 가진다고 가정해보자. 전문가 가중치는 총 800개다. 그중 2개만 선택하면 이번 계산에 사용하는 전문가 가중치는 200개다. 이 예시에서는 router와 공통 연산의 가중치를 제외했다.

실제 모델의 활성 파라미터를 셀 때는 선택한 전문가 외에 공통으로 사용하는 부분도 포함해야 한다. 그래서 전문가 선택 비율만 전체 모델 크기에 곱하면 맞지 않을 수 있다.

Mixtral 논문은 전체 약 47B와 토큰당 활성 약 13B를 구분한다. B는 10억을 뜻하므로 각각 약 470억 개와 130억 개다. 8x7B라는 이름을 독립적인 7B 모델 8개가 들어 있다는 뜻으로 읽으면 안 된다. attention 등 공유되는 부분이 있기 때문이다. 또한 13B는 항상 똑같은 가중치 묶음을 고정해서 사용한다는 의미도 아니다. 토큰과 층에 따라 선택되는 전문가가 달라진다. Mixtral of Experts의 수치다.

활성 파라미터가 적으면 연산량을 줄일 여지가 생긴다. 하지만 같은 활성 파라미터 수의 Dense 모델과 품질이나 속도가 반드시 같다는 뜻은 아니다. 두 모델의 구조와 학습 조건, 실제 실행 방식까지 다르다.

적게 계산해도 나머지 가중치는 보관해야 한다

예시에서 이번 토큰이 전문가 2개만 사용했다고 나머지 6개를 버릴 수는 없다. 다음 토큰이나 다른 입력에서는 그 전문가가 선택될 수 있기 때문이다. 가중치를 매번 다시 학습하는 것도 아니므로 필요한 시점에 불러올 수 있는 곳에 보관해야 한다.

여기서 계산량과 메모리 요구량이 갈라진다. 한 토큰에서 읽어 계산하는 가중치가 적어도 모델 전체의 가중치는 여전히 존재한다. 일반적인 GPU 상주 구성에서는 전체 가중치를 담을 공간이 필요하다. Hugging Face의 서빙 설명도 MoE의 적은 계산량과 큰 메모리 요구를 함께 다룬다.

모든 가중치가 반드시 GPU 한 장에 있어야 하는 것은 아니다. 여러 GPU에 나누거나 RAM과 저장장치에 일부를 두는 구현도 가능하다. 다만 필요한 가중치가 계산할 장치에 없다면 옮기거나 다른 장치에서 계산하는 비용을 감수해야 한다. 활성 파라미터만큼의 VRAM이면 아무 조건 없이 실행된다고 볼 수는 없다.

실제 추론 메모리에는 가중치 외에 이전 토큰의 attention 계산에 쓰는 값을 보관하는 KV 캐시와 중간 결과, 실행 버퍼도 들어간다. 양자화는 가중치를 더 적은 비트로 저장하는 방법이고 MoE는 일부 전문가를 선택해 계산하는 구조다. 둘을 함께 사용할 수 있지만 줄이려는 비용과 작동 방식은 구분해야 한다.

router가 한쪽으로 쏠리는 문제도 있다

전문가를 여러 개 두었다고 학습이 자동으로 골고루 진행되지는 않는다. router가 일부 전문가에만 토큰을 계속 보내면 그 전문가에 학습과 계산이 몰리고 다른 전문가들은 충분한 학습 기회를 얻지 못할 수 있다.

이를 줄이기 위해 전문가 사용량이 한쪽에 치우치지 않도록 보조 학습 목적을 두는 방식이 있다. Switch Transformer는 부하 균형을 위한 보조 손실과 전문가별 처리 용량을 설명한다. 그 논문의 구성에서는 특정 전문가의 용량을 넘는 토큰이 생길 수 있고 용량을 늘리면 계산과 통신 비용도 증가한다. Switch Transformer의 2.2절을 참고했다.

학습 방법도 처음부터 MoE를 학습하는 경우만 있는 것은 아니다. 카카오의 Kanana-MoE 개발기에서는 기존 Dense 모델을 활용하는 upcycling을 설명한다. 기존 MLP 가중치를 바탕으로 전문가를 구성한 뒤 추가 학습하는 접근이다. 단순히 복제해놓는 것만으로 완성된 모델이 되는 것은 아니다.

실제 속도는 비교 기준과 실행 환경에 달려 있다

“MoE가 Dense보다 빠르다”는 설명을 읽을 때는 무엇을 같게 놓고 비교하는지부터 확인해야 한다. 전체 파라미터 수가 같은 비교와 비슷한 품질을 내는 모델끼리의 비교는 다른 질문이다.

모델 크기 한 가지로 우열을 정하기 어려운 이유
비교 기준확인할 것
같은 전체 파라미터 수MoE는 일부 전문가만 계산하지만 routing과 통신 비용이 추가된다.
같은 활성 파라미터 수저장할 전체 가중치와 계산 경로가 다르므로 같은 속도를 보장하지 않는다.
비슷한 품질같은 과제로 품질을 평가한 뒤 지연과 처리량, 메모리 요구를 비교해야 한다.
같은 학습 예산학습 효율의 비교다. 그 결과를 추론 속도의 배율로 옮길 수는 없다.

선택된 전문가가 여러 GPU에 나뉘어 있으면 토큰의 벡터와 결과를 주고받아야 한다. 전문가별로 배정되는 토큰 수가 다르면 한쪽 계산이 먼저 끝나도 다른 쪽을 기다릴 수 있다. 여러 토큰을 한 번에 처리하면 토큰마다 고른 전문가가 달라 전체적으로 많은 전문가가 사용될 수도 있다. 연산량 감소가 그대로 응답 시간 감소가 되지는 않는다. NVIDIA의 기술 글은 이 라우팅과 부하 분포를 분석한다.

또한 긴 입력을 처음 읽는 prefill과 답변을 이어 쓰는 decode는 처리 양상이 다르다. 모델을 고를 때는 초당 생성 토큰뿐 아니라 첫 응답까지의 시간과 전체 완료 시간도 확인해야 한다. 단일 요청이 빨리 끝나는 것과 여러 요청을 많이 처리하는 것도 따로 봐야 한다.

다음 질문은 어디에 두고 계산할지였다

Dense와 MoE를 비교하고 나니 큰 모델의 일부만 계산한다는 설명과 작은 GPU에서 실행할 수 있다는 설명 사이에 무엇이 빠져 있었는지 보였다. 모델이 어떤 전문가를 선택하는지는 계산 구조의 문제다. 선택된 전문가의 가중치를 어디에 두고 어느 장치에서 계산할지는 실행 방식의 문제다.

GPU 캐시와 CPU 계산, RAM과 SSD의 역할은 이어지는 글 Strata는 작은 VRAM으로 큰 MoE 모델을 어떻게 실행할까에서 실제 배치와 측정 기록을 함께 정리했다.
