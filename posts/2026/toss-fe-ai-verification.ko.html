Study note / Video-based original rewrite

이 글은 토스 챌린저스의 발표 영상 「토스 FE 개발자들의 검증법」을 보고 정리한 공부 기록이다. 발표 내용을 그대로 옮기지 않고, 공개된 화면과 설명을 바탕으로 AI 시대의 프론트엔드 검증을 어떻게 설계할 수 있을지 내 관점에서 다시 구성했다.

AI가 코드를 만드는 속도는 빨라졌다.
그런데 그 코드를 믿는 속도까지 빨라진 것은 아니다.

프론트엔드 개발의 많은 단계에 AI가 들어오고 있다. 스펙을 정리하고, 디자인을 분석하고, 컴포넌트를 만들고, 코드를 리뷰하고, 배포를 준비하는 일까지 에이전트가 도와준다. 결과물의 양은 분명히 늘어난다.

문제는 그다음이다. 내가 직접 작성하지 않은 코드가 실제 사용자에게도 괜찮은지 확인하려면 결국 화면을 열고, 버튼을 누르고, 여러 상태를 통과해보고, 실패했을 때 다시 재현해야 한다. 생성 속도가 빨라질수록 검증이 병목이 된다.

토스의 Frontend AI Team이 발표에서 보여준 것은 이 병목을 단순히 테스트 코드 생성으로 해결하는 방법이 아니었다. 실제 디바이스를 조작할 수 있는 환경, 그 행동을 테스트 코드로 바꾸는 흐름, 실패를 영상과 로그로 재현하는 도구를 하나의 시스템으로 묶는 방법이었다.

프론트엔드 워크플로의 마지막에 남은 일

발표 화면의 워크플로는 스펙 논의에서 시작해 디자인 분석, 코드 작성, 자체 검증, 알파 배포, QA와 승인, 라이브 배포, CS 대응으로 이어진다. 마지막 단계에서 발견한 문제는 다시 스펙 논의로 돌아간다. 제품 개발은 직선이 아니라 반복되는 고리다.

AI는 이 고리의 여러 부분을 빠르게 만든다. 하지만 검증은 여전히 사람의 손에 남기 쉽다. QA 리소스가 있는 팀은 QA에 의존하고, 그렇지 않은 팀은 개발자들이 함께 화면을 확인한다. 테스트를 만들고 싶어도 환경을 준비하고, 테스트 계정을 만들고, 외부 브라우저와 앱을 오가고, 필요한 데이터를 되돌리는 일까지 생각하면 시작하기가 무겁다.

테스트가 필요하지 않은 것이 아니라, 테스트를 만들 수 있는 환경이 없었던 것이다.

코드에서 테스트를 뽑아내려던 첫 번째 시도

처음에는 코드베이스를 진실의 원천으로 보았다. 코드 안에는 화면과 로직이 있고, PRD와 제품의 흐름도 어느 정도 담겨 있다. 그렇다면 AI가 코드를 읽고 화면 흐름을 추론한 뒤 시나리오를 만들고 E2E 테스트까지 생성할 수 있을 것 같았다.

하지만 코드에는 중요한 정보가 빠져 있었다. 무엇이 반드시 지켜져야 하는지, 사용자가 어느 지점에서 이탈하면 안 되는지, 기획자와 디자이너가 어떤 의도로 화면을 만들었는지는 코드만 읽어서 완전히 복원하기 어렵다. 정보가 부족해서가 아니라, 오히려 코드에 너무 많은 구현 세부사항이 섞여 있어 중요한 의도를 구분하기 어려운 것이다.

이 문제를 해결하기 위해 발표팀은 서비스 개발자들을 직접 만났다. 그 결과 E2E가 없는 이유는 필요성을 몰라서가 아니라 만들고 유지할 여력이 없어서라는 사실을 확인했다. 접근 방식은 코드에서 테스트를 추측하는 방향에서, 실제 사용자가 하는 일을 관찰하고 그것을 테스트로 남기는 방향으로 바뀌었다.

좋은 E2E는 테스트 코드보다 환경에서 시작한다

발표에서 말하는 E2E의 방향은 세 가지로 정리된다.

  1. 모킹에 기대지 않는다. 테스트만을 위한 가짜 흐름보다 실제 사용자가 경험하는 표면에 가깝게 접근한다.
  2. 재현 가능해야 한다. 실행할 때마다 결과가 달라지는 외부 요인을 줄이고 기계적인 환경을 다시 만들 수 있어야 한다.
  3. AI를 생산과 유지보수에 함께 사용한다. 테스트를 한 번 생성하는 것보다, 계속 살아 있게 만드는 비용을 줄이는 것이 중요하다.

여기서 중요한 표현은 Testable한 환경이다. 테스트 코드를 잘 쓰는 것만으로는 충분하지 않다. 테스트 계정을 만들 수 있어야 하고, 필요한 상품과 미션을 준비할 수 있어야 하며, 인증과 네이티브 앱 동작도 통제할 수 있어야 한다. 테스트가 자산이 되려면 테스트를 만들고 다시 실행할 기반이 먼저 자산이어야 한다.

테스트를 위해 새로 만든 API들

실제 테스트를 만들기 시작하면 곧바로 다른 팀의 도움이 필요해진다. 얼굴 결제 영역에서는 테스트용 본인 인증과 검증 데이터가 필요하고, 쇼핑 흐름에서는 테스트 상품을 만들고 검색할 수 있어야 한다. 인증이 필요한 미션은 테스트 유저가 통과할 수 있는 별도의 장치가 있어야 한다.

발표 화면에는 얼굴 결제, 상품 생성, 정부기관 인증, 광고 미션 생성이 각각 테스트 가능한 API로 정리되어 있다. 이런 API는 처음부터 준비되어 있던 공용 기능이 아니라, E2E를 만들면서 실제로 부족한 지점을 발견하고 여러 팀과 협의해 추가한 것들이다.

이 지점에서 E2E 테스트는 테스트팀만의 일이 아니게 된다. 서비스팀은 제품의 상태를 준비할 수 있는 인터페이스를 제공하고, 플랫폼팀은 실행 환경과 도구를 만들고, 디바이스팀은 실제 기기를 안정적으로 조작할 수 있게 한다. 검증 자동화는 코드 한 파일을 추가하는 일이 아니라, 제품을 테스트 가능한 형태로 바꾸는 작업에 가깝다.

에이전트에게는 눈과 손이 필요하다

발표에서 가장 흥미로운 장면은 에이전트가 실제 휴대폰을 조작하는 화면이었다. VS Code 안에 디바이스 화면이 보이고, 그 옆에는 화면 구조와 클릭 가능한 요소가 표시된다. 오른쪽 터미널에서는 에이전트가 로그인, 화면 이동, 클릭, 대기 같은 동작을 수행한다.

이 구조는 단순히 모바일 화면을 원격으로 보는 도구가 아니다. 화면 캡처, DOM 정보, 로그, 실행 가능한 액션을 함께 제공한다. 에이전트는 이미지 하나만 보고 추측하는 대신, 현재 화면에 어떤 요소가 있고 어떤 요소를 누를 수 있는지 확인하면서 다음 행동을 선택할 수 있다.

발표팀은 이 기능을 위해 Device Farm을 에이전트가 사용할 수 있는 형태로 감쌌다. 화면을 볼 수 있고, 기기를 조작할 수 있고, 조작 결과를 다시 확인할 수 있어야 에이전트가 개발자의 손을 보조할 수 있다. 에이전트에게 컨텍스트만 던지는 것과, 실제로 움직일 수 있는 도구를 주는 것은 전혀 다른 경험이다.

사람이 실기기에서 해본 일을 그대로 E2E로

테스트 작성 과정은 다음과 같다.

  1. 자연어로 만들고 싶은 테스트를 설명한다.
  2. 에이전트에게 새 유저 생성과 디바이스 로그인을 맡긴다.
  3. 실제 기기 화면을 보며 에이전트가 다음 동작을 수행하게 한다.
  4. 필요한 순간에는 개발자가 직접 클릭하거나 방향을 수정한다.
  5. 완료된 행동과 로그를 기반으로 E2E 코드를 생성한다.

이 방식의 장점은 테스트 작성자가 처음부터 셀렉터, 대기 시간, 예외 처리의 세부사항을 모두 알고 있지 않아도 된다는 점이다. 먼저 실제 사용자 흐름을 완성하고, 그 과정을 나중에 테스트 코드로 고정한다.

물론 한 번에 완벽하게 만들어지는 것은 아니다. 에이전트가 막히는 지점이 생기면 새로운 도구를 추가하고, 로그를 보강하고, 디바이스 조작 API를 개선한다. 테스트를 쉽게 만드는 과정 자체가 도구를 계속 발전시키는 과정이다.

깨지는 테스트를 없애는 대신, 빨리 고칠 수 있게 만들기

E2E 테스트는 만들기보다 유지하기가 어렵다. 제품의 문구나 화면 구조가 조금만 바뀌어도 테스트가 실패한다. 만든 사람이 자리를 옮기거나 테스트를 만든 의도를 잊으면, 실패 원인을 파악하지 못한 채 테스트를 건너뛰거나 삭제하게 된다.

발표에서 보여준 예시는 단순하지만 현실적이다. 테스트 코드는 미션하러 가기라는 버튼을 찾고 있었는데, 실제 제품의 문구가 구경하러 가기로 바뀌었다. 기능의 흐름은 크게 달라지지 않았지만 텍스트가 달라져 테스트는 버튼을 찾지 못했다.

이를 위해 실패한 테스트는 단순히 에러 메시지만 남기지 않는다.

  • 실패 순간의 디바이스 화면을 영상으로 저장한다.
  • 기기 제어 API와 시스템 이벤트를 JSONL 로그로 남긴다.
  • 실행된 코드, 스크린 덤프, 화면 요소 정보를 함께 보존한다.

이 자료가 있으면 개발자는 “어디에서 실패했는가”뿐 아니라 “그때 화면에 무엇이 있었는가”를 바로 확인할 수 있다. 에이전트도 같은 자료를 받아 변경된 버튼 문구나 화면 구조를 추론하고, 테스트 코드를 수정할 수 있다.

처음부터 AI가 테스트를 고치게 하려고 만든 기능은 아니었다고 한다. CI에서 테스트가 깨졌을 때 사람이 쉽게 상황을 이해하도록 만든 Replay가, 결과적으로 AI에게도 좋은 입력이 된 것이다. 사람이 읽기 좋은 관찰 도구가 에이전트에게는 문제 해결 도구가 된다.

AI를 잘 쓰는 방법은 좋은 도구를 만드는 것

발표의 가장 일반적인 교훈은 다음 문장으로 정리할 수 있다.

AI에게 컨텍스트를 제공하는 데서 끝내지 말고, 사람이 쓰기 좋은 도구를 만들어 AI에게 넘겨라.

발표 화면의 세 가지 도구는 서로 역할이 다르다.

  • 로그 분석과 시나리오 생성: 실제 사용자의 로그와 logging system 구조를 에이전트가 읽고 테스트 시나리오로 바꾼다.
  • 에이전트 기기 제어: Device Farm을 에이전트가 직접 조작할 수 있도록 한다.
  • 테스트 상황 재현: 깨진 테스트의 영상과 로그를 Replay로 복구해 원인을 찾고 수정한다.

AI 모델의 능력만 바뀌기를 기다리는 대신, 모델이 사용할 수 있는 인터페이스를 제품에 맞게 설계한 것이다. 에이전트가 무엇을 알고 있는지보다, 무엇을 실제로 확인하고 조작할 수 있는지가 중요해진다.

플랫폼 도구도 결국 제품이다

도구를 만드는 팀은 기술에 매몰되기 쉽다. 내부적으로는 멋지고 자동화된 기능이어도, 실제 개발자가 자기 워크플로에 넣을 이유가 없다면 사용되지 않는다.

발표자는 모든 팀을 조금씩 돕는 도구보다, 몇몇 팀의 문제를 확실히 해결하는 도구가 먼저라고 말한다. 얼굴 결제나 쇼핑처럼 오류 비용이 큰 팀과 함께 시작한 것도 같은 이유다. 강한 필요가 있는 사용자와 붙어야 테스트 도구가 어떤 기능을 가져야 하는지 선명해진다.

이 과정에서 동료의 역할도 컸다. 이미 잘 만들어진 logging system이나 Device Farm이 있는지 주변에 물어보고, 비슷한 문제를 해결하고 있는 팀의 기능을 가져다 쓰고, 필요한 API를 요청했다. 막힐 때마다 동료에게 질문할 수 있는 문화가 작은 플랫폼팀이 큰 기반을 만드는 데 도움을 준 것이다.

다음 단계는 ‘믿을 수 있는 딸깍’이다

발표의 마지막에는 두 가지 방향이 제시된다.

첫째는 기반을 단단하게 만드는 일이다. 지금 있는 도구를 더 안정적으로 만들고, 테스트 실행 시간을 줄이고, 흔들리지 않는 환경을 만드는 것. 실제 디바이스에서 검증하는 만큼 현실적인 신뢰를 얻을 수 있지만, 그만큼 실행 시간이 길어질 수 있기 때문이다.

둘째는 개발 워크플로 전체를 연결하는 일이다. 스펙 문서에서 시나리오와 E2E 테스트를 자동으로 도출하고, 그 테스트를 통과하는 코드를 자동으로 작성하는 흐름이다. 개발과 테스트가 따로 움직이지 않고 하나의 고리로 연결되면, AI가 만든 결과물을 더 빠르게 확인하고 다시 수정할 수 있다.

여기서 말하는 미래는 단순히 버튼 하나로 모든 것이 끝나는 자동화가 아니다. 실패했을 때 무엇이 바뀌었는지 확인할 수 있고, 언제든 같은 상황을 재현할 수 있으며, 깨진 테스트를 빠르게 고칠 수 있는 자동화다. 딸깍할 수 있지만 믿을 수 있는 딸깍에 가깝다.

마치며

이 발표를 보고 나서 E2E 테스트를 바라보는 방식이 달라졌다. 테스트 코드를 잘 작성하는 문제라고 생각했지만, 실제로는 테스트가 살아 있을 수 있는 환경을 만드는 문제에 더 가깝다.

AI가 코드를 빠르게 만들수록 검증은 더 중요해진다. 그리고 검증을 AI에게 맡기려면 AI에게 화면을 보여주고, 기기를 조작하게 하고, 실패 당시의 상황을 다시 재생하게 해야 한다. 결국 AI 활용의 핵심은 프롬프트를 길게 쓰는 데만 있지 않다. AI가 실제 제품의 맥락 안에서 사용할 수 있는 도구를 설계하는 데 있다.

좋은 E2E는 테스트 파일 하나가 아니다. 실제 사용자 흐름, 테스트 가능한 API, 디바이스 팜, 실행 로그, 실패 영상, Replay, 그리고 그것을 함께 개선하는 동료까지 포함한 하나의 개발 환경이다.
