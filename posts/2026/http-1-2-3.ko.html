브라우저가 같은 연결에서 큰 이미지를 먼저 요청하고 작은 CSS 파일을 이어서 요청했다고 하자. 이미지 응답이 늦어지면 CSS도 기다려야 할까? HTTP 버전에 따라 답이 달라진다.

HTTP/1.1은 요청 순서대로 응답을 보낸다

HTTP/1.1은 TCP 연결 하나를 여러 요청에 재사용한다. 파이프라이닝을 쓰면 이미지 응답이 오기 전에 CSS도 요청할 수 있다. 서버가 두 GET 요청을 병렬로 처리하더라도 이미지 응답을 다 보낸 뒤에야 CSS 응답을 보낼 수 있다.

준비된 CSS가 앞 응답 때문에 기다리는 현상이 HOL(Head-of-Line) 블로킹이다. 브라우저는 같은 서버에 연결을 여러 개 열어 CSS를 별도로 받을 수 있다. 대신 연결을 열고 유지하는 비용이 든다. RFC 9112의 연결 재사용과 파이프라이닝

HTTP/2는 한 연결에서 여러 응답을 섞어 보낸다

스트림은 한 연결 안에서 요청과 응답이 오가는 통로다. HTTP/2는 이미지와 CSS를 각각 다른 스트림에 싣고 프레임이라는 작은 단위로 나눠 섞어 보낸다. 이 방식을 멀티플렉싱이라고 한다. 이미지 전송 중에도 CSS를 먼저 받을 수 있다.

TCP는 한 연결에 들어온 바이트를 순서대로 전달한다. 앞쪽의 이미지 데이터가 유실되면 뒤쪽의 CSS 데이터가 이미 도착했어도 TCP는 빠진 구간이 복구될 때까지 기다린다. 이 경우 병목은 HTTP 응답 순서에서 TCP의 바이트 전달 순서로 옮겨간다. RFC 9113의 멀티플렉싱과 TCP 블로킹

HTTP/3은 스트림마다 순서를 맞춘다

HTTP/3은 UDP 위에서 동작하는 QUIC을 쓴다. QUIC은 유실된 데이터를 다시 보내고 스트림마다 순서를 따로 맞춘다. 이미지 데이터만 담긴 패킷이 유실되면 CSS 스트림은 계속 진행할 수 있다. 두 스트림의 데이터가 같은 패킷에 들어 있었다면 둘 다 복구를 기다린다. RFC 9000의 패킷과 스트림

새 연결을 맺는 방식도 다르다. HTTPS에서 HTTP/1.1과 HTTP/2는 보통 TCP 연결을 맺은 뒤 TLS를 협상한다. QUIC은 연결을 맺는 과정에 TLS 1.3 핸드셰이크를 포함해 왕복 횟수를 줄일 수 있다. UDP가 막힌 네트워크에서는 TCP 기반 HTTP로 다시 연결할 수 있다. RFC 9114의 HTTP/3 개요, 연결 설정
