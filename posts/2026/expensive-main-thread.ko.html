프론트엔드 성능을 공부하다가 결국 하나의 질문으로 돌아왔다.
이 작업은 정말 지금 메인 스레드에서 처리해야 할까?

웹사이트가 느려졌을 때 가장 먼저 떠올리는 것은 네트워크 요청이나 번들 크기다. 이미지를 줄이고, 캐시를 붙이고, 자바스크립트 파일을 나누는 방법부터 찾게 된다. 물론 중요한 문제들이다. 하지만 화면이 복잡해질수록 또 다른 병목이 모습을 드러낸다. 코드가 실행되고 화면이 그려지는 브라우저의 메인 스레드다.

스크롤이 끊기거나 버튼을 눌렀는데 반응이 늦고, 검색창에 입력한 글자가 한 박자 뒤에 나타나는 경험은 메인 스레드가 다른 일을 처리하느라 사용자의 입력을 제때 받지 못할 때 발생한다. 이때 문제는 반드시 함수 하나가 느리다는 뜻이 아니다. 그 작업이 사용자와 화면이 함께 사용하는 통로를 너무 오래 점유하고 있다는 뜻에 가깝다.

kciter.so의 「브라우저의 메인 스레드는 비싸다」를 읽으며, 메인 스레드의 일을 줄이고 나누는 방법을 정리했다. 핵심은 작업을 더 빠르게 만드는 데만 있지 않았다. 작업의 크기와 순서를 조절하고, 필요하다면 다른 스레드로 보내고, 애초에 하지 않아도 되는 일은 없애는 것이었다.

메인 스레드는 무엇을 하는가

브라우저에는 여러 스레드가 있지만 웹 개발자가 직접 작성한 자바스크립트 대부분은 메인 스레드에서 실행된다. 이벤트 핸들러, 타이머, 네트워크 응답 콜백, 프레임워크의 내부 동작이 모두 이곳에서 처리된다.

화면을 갱신하는 과정도 메인 스레드의 일이다. DOM이나 스타일이 바뀌면 브라우저는 대략 다음 순서로 한 프레임을 준비한다.

  • requestAnimationFrame 콜백 실행
  • 스타일 계산
  • 레이아웃 계산
  • 페인트 명령 생성

그 결과를 실제 화면에 합치는 합성 단계는 컴포지터 스레드가 맡을 수 있지만, 그 앞의 대부분은 메인 스레드의 몫이다. 결국 자바스크립트 실행과 화면 갱신이 한 줄에 함께 선다.

60Hz 화면은 초당 60개의 프레임을 그려야 하므로 한 프레임에 주어진 시간은 약 16.6ms다. 브라우저 자체의 처리 시간까지 생각하면 애플리케이션이 사용할 수 있는 시간은 대략 10ms 남짓으로 봐야 한다. 이 시간보다 훨씬 긴 작업이 실행되면 그동안 클릭, 입력, 렌더링이 모두 기다려야 한다. 보통 50ms를 넘겨 메인 스레드를 붙잡는 작업을 롱 태스크라고 부르는 이유다.

메인 스레드 안에서 시간을 나누어 쓰기

메인 스레드에서 처리해야만 하는 일이 있다면, 한 번에 독점하지 않도록 만드는 방법을 먼저 생각할 수 있다. 이를 네 가지 관점으로 나눠볼 수 있다. 작업을 쪼개고, 여러 요청을 모으고, 급한 일을 먼저 처리하고, 급하지 않은 일은 미루는 것이다.

1. 긴 작업은 쪼갠다

실시간 채팅처럼 한 번에 많은 데이터가 들어오는 상황을 생각해보자. 메시지 수백 개를 한 번에 DOM에 추가하면 브라우저는 그 작업이 끝날 때까지 다른 일을 처리할 수 없다. 채팅을 그리는 작업 자체가 빨라지지는 않지만, 작은 묶음 사이에 메인 스레드를 잠깐 돌려주면 입력과 화면 갱신이 끼어들 자리가 생긴다.

작업을 한 번에 처리할까, 나눠 처리할까

같은 계산량을 한 번에 처리하는 방식과 프레임마다 5ms만 사용하는 방식을 비교한다. 실행 중 입력창에 타이핑하면서 차이를 느껴보자.

0 / 500,000 units

준비됨 · 계산 방식을 선택하세요.

가장 단순한 방법은 다음 작업을 새로운 태스크로 예약하는 것이다.

const yieldToBrowser = () =>
  new Promise((resolve) => setTimeout(resolve, 0));

async function renderMessages(messages) {
  for (let i = 0; i < messages.length; i += 20) {
    const batch = messages.slice(i, i + 20);
    appendMessageNodes(batch);
    await yieldToBrowser();
  }
}

await이 작업을 멈추고, setTimeout이 다음 태스크를 예약한다. 현재 태스크가 끝난 뒤 브라우저는 밀려 있던 입력과 렌더링을 처리할 수 있다. 중요한 점은 양보가 전체 처리 시간을 줄여주지는 않는다는 것이다. 오히려 예약과 재개에 드는 비용 때문에 총 시간은 늘어날 수 있다. 대신 사용자가 기다리는 동안 화면이 완전히 멈추지 않게 한다.

작업량을 개수가 아니라 시간으로 나눠야 할 때도 있다. 각 데이터의 처리 시간이 서로 다르거나 애니메이션과 동시에 실행되는 작업이라면, 한 프레임에 쓸 예산을 정해두고 다음 프레임에서 이어가는 편이 안전하다.

async function processInFrameBudget(items) {
  let index = 0;

  while (index < items.length) {
    const frameStart = await new Promise(requestAnimationFrame);

    while (
      index < items.length &&
      performance.now() - frameStart < 5
    ) {
      doWork(items[index]);
      index += 1;
    }
  }
}

여기서 5ms는 법칙이 아니라 휴리스틱이다. 한 프레임의 남은 시간을 모두 배경 작업에 써버리지 않고, 애니메이션과 스타일 계산이 사용할 여유를 남겨두기 위한 값이다. 작업을 너무 잘게 나누면 양보하는 비용이 더 커질 수 있고, setTimeout은 반복 호출 시 최소 지연 시간의 영향을 받을 수 있다는 점도 기억해야 한다. 필요에 따라 MessageChannel이나 scheduler.yield()를 검토할 수 있지만 브라우저 지원 범위와 작업의 특성을 함께 봐야 한다.

2. 너무 잦은 작업은 모은다

쪼개기가 작업 하나의 크기를 줄이는 방법이라면, 모으기는 반복되는 작업의 횟수를 줄이는 방법이다. 스크롤, 리사이즈, 입력 이벤트는 짧은 시간에 매우 많이 발생할 수 있다. 이벤트마다 무거운 계산을 실행하면 작업을 아무리 잘게 나눠도 요청이 계속 쌓인다.

입력이 끝난 뒤 한 번만 실행하면 되는 검색 요청에는 디바운스를 적용할 수 있다. 반대로 스크롤 위치처럼 일정한 간격으로 최신 상태를 반영하면 되는 작업에는 스로틀을 사용할 수 있다. 화면을 그리는 작업은 requestAnimationFrame에 묶어 프레임당 한 번만 실행하는 방식도 유용하다.

let renderScheduled = false;

function requestBoardRender() {
  if (renderScheduled) return;
  renderScheduled = true;

  requestAnimationFrame(() => {
    renderBoard();
    renderScheduled = false;
  });
}

socket.addEventListener('tick', (event) => {
  storeTick(event.detail); // 데이터는 모아둔다
  requestBoardRender();    // 화면은 프레임당 한 번만 갱신한다
});

이 방식은 데이터를 버리는 것과 다르다. 들어온 데이터를 저장하되, 화면에 반영하는 횟수만 줄인다. DOM을 하나씩 수정하는 대신 여러 노드를 한 번에 추가하거나, 여러 스타일 변경을 클래스 하나의 변경으로 바꾸는 것도 같은 원리다. 반복되는 고정 비용을 한 번으로 접는 것이다.

3. 급한 일을 먼저 처리한다

메인 스레드에서는 작업의 순서가 곧 반응성이다. 사용자가 방금 누른 버튼의 결과는 빠르게 보여줘야 하지만, 화면 밖 통계를 미리 계산하는 일은 잠시 늦어도 괜찮을 수 있다. 모든 작업을 같은 우선순위로 처리하지 않는 것이 중요하다.

이를 간단한 큐로 표현할 수 있다. 평범한 작업은 뒤에 넣고, 사용자가 직접 요청한 작업은 앞에 넣는다.

const jobs = [];
const channel = new MessageChannel();

channel.port1.onmessage = () => {
  const job = jobs.shift();
  if (!job) return;

  job.run();
  if (jobs.length > 0) channel.port2.postMessage(null);
};

function enqueue(job, urgent = false) {
  urgent ? jobs.unshift(job) : jobs.push(job);
  if (jobs.length === 1) channel.port2.postMessage(null);
}

예를 들어 사진 여러 장의 미리보기를 만드는 작업은 순서대로 처리해도 된다. 하지만 사용자가 아직 만들어지지 않은 특정 사진을 클릭했다면, 그 사진의 미리보기만 큐 앞으로 가져오는 편이 낫다. 전체 처리량은 같아도 사용자가 중요하다고 느끼는 결과를 먼저 보여줄 수 있기 때문이다. 한가할 때 미리 처리하다가 필요해지는 순간 우선순위를 높이는 접근을 idle-until-urgent라고 한다.

4. 급하지 않은 일은 미룬다

가장 확실한 최적화는 지금 하지 않아도 되는 일을 나중으로 보내는 것이다. 초기 화면에 필요하지 않은 코드는 코드 스플리팅으로 나눠 필요한 시점에 불러올 수 있다. 화면 밖 콘텐츠는 미리 전부 만들지 않고, 가까워졌을 때 채우는 방법도 있다.

const observer = new IntersectionObserver(
  (entries) => {
    for (const entry of entries) {
      if (entry.isIntersecting) {
        hydrate(entry.target);
      } else {
        releaseHeavyContent(entry.target);
      }
    }
  },
  { rootMargin: '400px' }
);

document.querySelectorAll('.feed-item').forEach((item) => {
  observer.observe(item);
});

이렇게 하면 화면 밖 요소의 DOM 생성과 유지 비용까지 미룰 수 있다. 화면 밖에서 계속 돌아가는 차트나 애니메이션도 멈추는 편이 좋다. content-visibility: auto가 비슷한 효과를 제공하지만, 브라우저별 동작 차이가 있을 수 있으므로 실제 지원 환경에서 확인해야 한다.

메인 스레드 밖에서 처리하기

작업을 나누고 모아도 메인 스레드에서 처리하기엔 너무 무거운 일이 있다. 이때는 그 일을 다른 곳으로 보내는 방향을 생각해야 한다. 다만 브라우저의 모든 스레드를 우리가 직접 제어할 수 있는 것은 아니다.

  • 메인 스레드: 자바스크립트, DOM, 스타일, 레이아웃, 이벤트
  • 컴포지터 스레드: 이미 그려진 레이어의 합성
  • 래스터 스레드: 페인트 명령을 픽셀로 변환
  • 워커 스레드: 별도로 만든 자바스크립트 실행 공간

컴포지터가 처리할 수 있는 애니메이션

transform과 opacity는 이미 그려진 레이어를 옮기거나 투명하게 만드는 속성이다. 레이아웃과 페인트를 매번 다시 계산하지 않아도 되기 때문에, 조건이 맞으면 메인 스레드를 거치지 않고 컴포지터에서 애니메이션을 진행할 수 있다.

반면 top, left, width, height를 애니메이션하면 매 프레임 레이아웃이 발생할 수 있다. 같은 상자를 움직이는 작업이라도 어떤 CSS 속성을 선택하느냐에 따라 메인 스레드의 부담이 달라진다. 위치 이동은 transform: translate, 크기 변화는 transform: scale을 우선 검토하는 이유다.

실제 레이아웃 변경이 필요한 목록 재정렬에는 FLIP 기법을 사용할 수 있다. 먼저 변경 전 위치를 측정하고(First), 레이아웃을 바꾼 뒤 새 위치를 측정한다(Last). 그 다음 새 요소에 반대 방향의 transform을 적용해 이전 위치에 있는 것처럼 보이게 만들고(Invert), transform을 제거하는 애니메이션을 재생한다(Play).

const before = item.getBoundingClientRect();

list.prepend(item);

const after = item.getBoundingClientRect();
const x = before.left - after.left;
const y = before.top - after.top;

item.animate(
  [
    { transform: `translate(${x}px, ${y}px)` },
    { transform: 'none' },
  ],
  { duration: 300, easing: 'ease-in-out' }
);

눈에는 요소가 옛 위치에서 새 위치로 이동하는 것처럼 보이지만, 실제 레이아웃 변경은 이미 끝난 뒤다. 움직이는 과정은 컴포지터가 처리할 수 있는 transform으로 표현한다. 다만 will-change는 남용하면 레이어와 메모리 사용량이 늘어날 수 있으므로 필요한 요소에만 사용해야 한다.

레이아웃 값을 읽는 코드와 스타일을 쓰는 코드가 뒤섞여도 문제가 생긴다. 스타일을 바꾼 직후 offsetWidth나 getBoundingClientRect()를 읽으면 브라우저가 최신 레이아웃을 계산하기 위해 즉시 작업할 수 있다. 이 패턴을 반복문에서 되풀이하면 레이아웃 스래싱이 된다. 읽기를 먼저 모으고, 쓰기를 나중에 모으는 습관이 필요하다.

계산은 웹 워커로 보낸다

대용량 데이터 파싱, 이미지 처리, 복잡한 수치 계산처럼 DOM과 직접 관련 없는 작업은 웹 워커로 옮길 수 있다. 워커가 계산하는 동안 메인 스레드는 입력과 화면을 담당할 수 있다.

const worker = new Worker('calculator.js');

worker.addEventListener('message', (event) => {

워커는 DOM에 접근할 수 없고 postMessage로만 메인 스레드와 통신한다. 데이터가 복사되기 때문에 계산이 가볍거나 주고받는 데이터가 크면 오히려 손해일 수 있다. 반대로 이미지 픽셀 처리처럼 계산량이 크고 DOM과 분리할 수 있는 작업에는 효과적이다.

큰 ArrayBuffer를 계속 복사해야 한다면 transferable object를 사용해 버퍼의 소유권을 넘길 수 있다. 이 경우 보낸 쪽에서는 해당 버퍼를 더 사용할 수 없지만, 큰 데이터를 복사하는 비용을 피할 수 있다.

worker.postMessage(
  { buffer: pixels.buffer, width, height },
  [pixels.buffer]
);

가장 빠른 최적화는 일을 없애는 것

작업을 쪼개고, 모으고, 우선순위를 정하고, 다른 스레드로 보내도 처리해야 할 일이 계속 쌓이면 한계가 온다. 실시간 데이터가 화면이 소화할 수 있는 속도보다 빠르게 들어오는 상황이 대표적이다. 이때는 모든 작업을 끝까지 처리하겠다는 생각을 버려야 한다.

첫 번째 방법은 버리기다. 실시간 로그처럼 최신 상태만 중요하고 과거 데이터가 화면에 꼭 남을 필요가 없다면 오래된 항목을 제거할 수 있다. 두 번째는 합치기다. 주가처럼 중간 값보다 최신 값만 의미 있는 데이터라면 밀린 업데이트를 하나로 합쳐 마지막 상태만 반영한다. 세 번째는 생략하기다. 같은 입력에 대한 계산 결과를 저장해두고 다시 사용하면 메모이제이션으로 반복 계산을 없앨 수 있다.

디바운스는 입력 중간의 불필요한 실행을 생략하고, 화면 밖 콘텐츠를 렌더링하지 않는 것은 보이지 않는 작업을 생략한다. 결국 성능 최적화의 상당 부분은 일을 잘 처리하는 기술인 동시에, 하지 않아도 되는 일을 찾아내는 기술이다.

마치며

메인 스레드 문제를 공부하면서 성능 최적화에 대한 관점이 조금 바뀌었다. 전에는 느린 코드를 찾고 더 빠른 알고리즘으로 바꾸는 것이 먼저라고 생각했다. 이제는 그보다 앞서 이 작업이 사용자 입력과 같은 스레드를 공유하는지, 한 프레임 안에 끝나야 하는지, 지금 당장 필요한지부터 확인해야 한다고 생각한다.

정리하면 선택지는 네 가지 질문으로 좁혀진다.

  • 작업을 작은 단위로 나눌 수 있는가?
  • 반복되는 실행을 한 번으로 모을 수 있는가?
  • 사용자에게 중요한 작업을 먼저 처리할 수 있는가?
  • 이 일을 늦추거나, 다른 스레드로 보내거나, 아예 없앨 수 있는가?

어떤 방법이 항상 정답인 것은 아니다. 양보에는 오버헤드가 있고, 워커에는 통신 비용이 있으며, 컴포지터를 활용하려면 레이아웃과 페인트의 차이를 이해해야 한다. 결국 성능은 기술 하나를 외우는 문제가 아니라, 상황에 맞는 트레이드오프를 선택하는 문제에 가깝다.
