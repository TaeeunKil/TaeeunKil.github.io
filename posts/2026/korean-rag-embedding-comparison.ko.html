문서가 많아지면서 본문 검색이 필요했다

사내 Mattermost 문서함에 문서가 많아지면서 필요한 자료를 찾는 일이 어려워졌다. 설치 안내서와 기능 설명서 외에도 결함 보고서와 운영 계획서 같은 자료가 섞여 있었다. 파일 이름을 알고 있으면 검색할 수 있지만 어떤 내용이 어느 문서에 있는지까지 기억하기는 어려웠다.

에이전트에게 파일을 하나씩 열어보게 할 수도 있다. 다만 문서가 많을수록 읽어야 하는 양과 도구 호출이 늘어난다. 질문과 관련된 본문 구간을 먼저 찾아주고 에이전트가 그 근거와 원문을 읽을 수 있게 하고 싶었다.

그래서 문서함에 RAG를 붙이는 방안을 검토했다. 문서의 본문을 추출해 검색 가능한 단위로 나누고 질문이 들어오면 관련 구간을 찾아 에이전트에 전달하는 구성이다. 보드와 이슈카드는 기존 키워드 검색과 필터를 유지하고 문서함의 본문 검색부터 대상으로 삼았다.

어떤 임베딩 모델을 쓸까

본문을 의미로 검색하려면 질문과 문서 내용을 벡터로 바꾸는 임베딩 모델이 필요했다. 어떤 모델을 쓰느냐에 따라 같은 질문에서도 검색 순위가 달라질 수 있다. 한국어로 작성된 업무 문서에서 관련 내용을 잘 찾는지와 기존 서비스가 사용하는 GPU에서 함께 운영할 수 있을지를 확인하고 싶었다.

기존 Open WebUI 환경에는 BGE-M3 서비스가 있었다. 그대로 사용할 수도 있었지만 다른 모델을 쓰면 검색 결과가 얼마나 달라지는지 궁금했다. 비교 대상으로 Qwen3-Embedding-4B와 한국어 검색용 KURE-v3를 골랐다. KURE-v3 공식 모델 카드는 한국어와 영어를 지원하는 1.1B dense 검색 모델로 소개한다.

공개 벤치마크의 점수만으로 모델을 정하기는 어려웠다. 실제 문서에는 비슷한 주제의 설명서와 결함 보고서가 함께 있고 파일을 찾는 것뿐 아니라 답에 필요한 구간을 가져오는 것도 필요했다. 먼저 공개 검색 데이터로 세 모델을 비교한 뒤 회사 문서에서도 같은 모델을 테스트하기로 했다. 검색 성능과 함께 처리 시간과 GPU 메모리를 측정했다.

같은 장비에서 임베딩 검색만 비교했다

2026년 11월 12일 같은 GPU 한 장에서 모델을 하나씩 순서대로 실행했다. 기존 서비스와 공존한 환경이라 전용 장비를 비워놓고 측정한 벤치마크는 아니다. 모든 모델에 fp16과 SDPA를 사용했고 배치 크기는 1로 맞췄다.

문서와 질문을 각각 벡터로 바꾸고 길이를 정규화한 뒤 코사인 유사도로 순위를 계산했다. 검색 대상의 모든 벡터와 직접 비교했으므로 근사 최근접 검색 색인의 오차는 없다. 키워드 검색을 결합하거나 리랭커로 순위를 다시 매기지 않았고 답변을 생성하는 LLM도 넣지 않았다. BGE-M3도 이번에는 dense 벡터만 사용했다.

이번 실행의 출력 차원과 입력 전처리. 최대 입력 길이는 모두 8,192토큰으로 설정했다.
모델차원질문 / 문서 입력
BGE-M31,024별도 접두어 없음
Qwen3-Embedding-4B2,560질문에 검색 지시문 / 문서는 접두어 없음
KURE-v32,048query: / passage:

입력 문자열을 억지로 같게 만들지는 않았다. 고정한 모델 revision의 Sentence Transformers 설정에서 query와 document 프롬프트를 읽었다. 설정이 없으면 빈 문자열을 사용했다. Qwen 질문에는 “Given a web search query”로 시작하는 기본 검색 지시문이 붙는다. 사내 문서에 맞춘 지시문 튜닝은 하지 않았다. 설정은 BGE-M3, Qwen, KURE-v3에서 확인할 수 있다.

8,192토큰은 이번 실험의 공통 설정이다. 각 모델이 지원하는 최대 길이가 모두 같다는 뜻은 아니다. 세 모델 모두 문서 입력이 이 제한을 넘어 잘린 경우는 없었다.

공개 데이터에서는 KURE-v3가 앞섰다

먼저 mteb/AutoRAGRetrieval의 전체 test 데이터를 사용했다. 검색 대상 텍스트 720개와 질문 114개, 질문과 정답의 관계를 담은 qrel 114행이다. 평가 스크립트는 직접 작성했지만 질문과 정답은 공개 데이터에 있는 것을 그대로 썼다.

이미 추출된 텍스트를 입력했으므로 PDF 파서의 품질을 평가한 실험은 아니다. MTEB 전체를 돌린 결과도 아니다. 한국어 검색 데이터셋 하나에서 얻은 비교값이다.

  • nDCG@10은 상위 10개 안에서 정답을 얼마나 앞에 놓았는지 평가한다. 높을수록 좋다.
  • Recall@10은 각 질문의 정답 중 상위 10개에 들어온 비율을 구하고 질문 전체에서 평균한 값이다.
  • Hit@5는 정답이 하나라도 상위 5개에 들어온 질문 수다.
공개 데이터: 질문 114개와 검색 대상 텍스트 720개. 점수는 소수 넷째 자리로 반올림했다.
모델nDCG@10Recall@10Hit@5
BGE-M30.83010.9737106 / 114
Qwen3-Embedding-4B0.84280.9912103 / 114
KURE-v30.93121.0000112 / 114

KURE-v3는 이 세 지표에서 모두 가장 높았다. Qwen은 BGE-M3보다 nDCG@10과 Recall@10이 높았지만 Hit@5는 낮았다. 같은 데이터에서도 몇 개까지 가져올지에 따라 비교가 달라졌다. KURE-v3를 다음 실험에 가져갈 이유는 충분했지만 회사 문서에서도 가장 잘 맞을지는 아직 알 수 없었다.

회사 문서에서는 파일과 근거의 순위를 나눴다

실제 공유 문서 30개를 골랐다. 핵심 문서 10개에 비슷한 주제의 방해 문서 20개를 더했다. 설치 안내서와 결함 보고서, 데이터 목록과 테스트 시나리오 등을 포함했고 형식은 PDF, DOCX, HWP, XLSX, Markdown이 섞여 있었다. 회사 원문은 서버 안에서 처리했으며 외부 서비스로 보내지 않았다.

PDF는 pypdf로 페이지별 텍스트를 뽑았다. DOCX는 ZIP 안의 XML에서 문단을 읽었고 HWP는 olefile로 본문 레코드를 읽었다. XLSX는 시트 이름과 셀의 열 참조를 남기고 첫 번째 비어 있지 않은 행을 헤더로 간주해 각 행에 붙였다. 복잡한 표의 헤더 구조까지 해석한 것은 아니다. Markdown은 문단 단위로 나눴다.

추출한 블록은 약 1,100문자까지 묶었다. 1,100문자를 넘는 긴 블록은 950문자 간격으로 잘라 최대 150문자가 겹치게 했다. 짧은 블록을 묶은 청크 사이에는 겹침을 따로 넣지 않았다. 제목을 제외한 본문 기준의 문자 단위 처리이며 토큰 단위 청킹은 아니다. 이렇게 만든 784개 청크에 각각 문서 제목을 붙여 임베딩했다.

민감한 문서는 제외하고 자격증명이 포함될 수 있는 줄을 거르는 필터도 적용했다. 다만 Markdown의 raw HTML이 남는 등 추출기는 아직 실험용이다. 모델 비교에는 같은 청크를 넣었지만 이 파서와 청킹이 최종 구성이라는 뜻은 아니다.

질문은 24개를 만들었다. 이 평가셋은 에이전트가 원문을 읽고 질문을 작성한 뒤 정답 문서와 근거 문자열(anchor)을 지정한 것이다. 직원들이 실제로 검색한 질문을 따로 모은 평가나 블라인드 평가가 아니다. 평가 전에는 지정한 문서의 청크 안에 모든 anchor가 들어 있는지 코드로 확인했다. 가능한 다른 정답 구간을 전부 판정하지는 않았다.

검색 점수는 청크마다 계산했지만 결과를 읽는 단위를 두 가지로 나눴다.

  1. 문서 순위는 청크를 유사도순으로 정렬한 다음 같은 문서의 중복을 제거했다. 따라서 문서에 속한 청크 중 최고 점수가 그 문서의 순위를 결정한다. 문서 전체를 하나의 벡터로 만든 검색은 아니다.
  2. 지정 근거 순위는 전체 784개 청크에서 정답 문서의 anchor를 포함한 청크가 처음 나오는 위치다. 해당하는 청크가 여러 개면 가장 앞선 순위를 쓴다.
문서 검색: 질문 24개와 문서 30개. Hit은 해당 순위 안에 정답 문서가 들어온 질문 수다.
모델문서 Hit@1문서 Hit@5문서 MRR
BGE-M316 / 2422 / 240.7717
Qwen3-Embedding-4B22 / 2424 / 240.9514
KURE-v320 / 2423 / 240.9005

MRR은 정답 문서 순위의 역수를 질문 전체에서 평균한 값이다. 정답이 1위면 1, 2위면 0.5로 계산하므로 정답을 앞에 놓을수록 높아진다. 파일 검색에서는 Qwen이 세 지표 모두 가장 높았다. 정답 파일을 첫 번째 결과로 보여주는 것이 우선이라면 이 결과는 Qwen을 고를 이유가 된다.

지정 근거 검색: 질문 24개와 청크 784개. Hit은 anchor를 포함한 정답 청크가 검색 범위 안에 들어온 질문 수다.
모델지정 근거 Hit@5지정 근거 Hit@10
BGE-M313 / 2417 / 24
Qwen3-Embedding-4B17 / 2421 / 24
KURE-v320 / 2421 / 24

상위 5개 청크만 가져오면 KURE-v3가 지정 근거를 더 자주 찾았다. 10개까지 넓히면 Qwen과 KURE가 21개 질문으로 같아졌다. 파일을 찾은 뒤 원문을 넓게 읽는 도구와 검색된 청크 몇 개를 바로 답변 모델에 넘기는 도구는 이 차이를 다르게 받아들일 수 있다.

공개 데이터와 회사 문서의 점수는 합치지 않았다. 검색 대상의 단위와 정답을 정한 방식이 다르다. 특히 지정 근거 Hit@5의 20/24를 “답변 정확도 83%”라고 부를 수는 없다. 답변 생성은 평가하지 않았고 라벨 밖에도 유효한 근거가 있을 수 있다.

정답 파일을 찾고도 근거는 멀리 있을 수 있었다

한 질문에서는 Qwen과 KURE가 모두 정답 문서를 2위에 올렸다. 그런데 미리 지정한 근거 청크는 KURE에서 3위였고 Qwen에서는 423위였다. 같은 파일 순위로는 이 차이가 보이지 않는다. 이 한 사례에서 Qwen이 다른 유효한 근거를 전혀 찾지 못했다고 단정할 수도 없다. 확실히 확인한 것은 지정한 구간의 순위 차이다.

세 모델이 모두 어려워한 질문도 있었다. 특정 조건에서 동작이 잘못된 결함 보고서를 찾으려는데 비슷한 조건을 다룬 일반 테스트 문서가 먼저 나왔다. 정답 문서는 Qwen에서 3위, BGE-M3에서 6위, KURE에서 9위였다. 관련 단어가 겹치는 문서 사이에서 실제 결함 상황과 일반 테스트의 맥락을 가르는 데 한계가 보였다.

평가 질문도 완벽하지 않았다. 대상을 “이 프로그램”으로만 표현해 무엇을 찾으려는지 모호한 질문이 있었다. 결과를 본 뒤 특정 모델에 유리하게 질문을 고치지는 않았다. 또 일부 질문에서는 anchor 밖의 다른 청크도 근거가 될 수 있었다. 다음 평가에서는 여러 정답 구간을 허용하고 질문 작성자와 다른 사람이 관련성을 검수할 필요가 있다.

처리 시간과 GPU 메모리 차이도 컸다

질문 인코딩 시간은 첫 질문으로 워밍업한 뒤 질문마다 한 번씩 측정했다. GPU 작업이 끝날 때까지 동기화한 시간을 기록했고 유사도 계산은 이 구간에서 제외했다. p50은 중앙값이고 p95는 측정값의 95번째 백분위수다. 이 값에는 네트워크와 DB 검색, 답변 생성 시간이 포함되지 않는다.

BGE-M3가 가장 빠르고 메모리도 적게 썼다. KURE는 회사 문서에서 BGE보다 질문 인코딩 중앙값이 약 2.16ms 길었고 Qwen은 KURE의 약 4.05배였다. 코퍼스 인코딩은 KURE가 BGE보다 약 2.39배 오래 걸렸다. 검색 때 질문 하나를 처리하는 비용과 문서를 처음 색인하거나 갱신하는 비용을 따로 볼 필요가 있었다.

메모리 수치는 torch.cuda.max_memory_allocated()로 측정했다. 모델을 로딩하고 워밍업한 다음 peak 통계를 초기화하고 문서와 질문을 인코딩하는 동안 기록한 값이다. PyTorch가 할당한 텐서 메모리의 최대치이며 nvidia-smi에 표시되는 전체 점유량이나 배포에 필요한 총 GPU 메모리와 같지 않다.

이 시간으로 운영 서비스의 p95나 동시 처리량을 예상하기는 어렵다. 질문 24개 또는 114개를 한 번씩 처리한 표본이고 동시 요청과 큐 대기, 배치 최적화는 시험하지 않았다. 기존 서비스의 부하도 엄격히 통제하지 않았다.

첫 후보는 KURE-v3지만 파일 검색의 장점은 Qwen에 남았다

내가 만들려는 도구는 관련 파일을 고른 뒤 에이전트가 근거와 원문 위치를 읽는 형태다. 이번 표본에서 KURE-v3는 지정 근거 Hit@5가 가장 높았고 질문 인코딩 시간도 BGE-M3에 가까웠다. 메모리 측정값도 Qwen보다 작아 기존 서비스와 함께 쓸 첫 후보로 제안했다.

반대로 파일을 첫 번째 결과로 정확히 보여주는 일이 가장 중요하다면 Qwen의 22/24를 가볍게 볼 수 없다. KURE보다 두 질문을 더 맞혔고 상위 5개 문서에는 24개 질문의 정답이 모두 들어왔다. 이 차이가 실제 사용자 질문에서도 유지되는지 확인한 뒤 처리 비용을 감수할지 판단해야 한다. BGE-M3도 가장 낮은 처리 비용을 가진 비교 기준으로 남는다.

질문 24개에서는 한 질문이 약 4.17%포인트를 차지한다. 제목을 청크마다 붙였으므로 제목 단서의 영향도 섞여 있다. 작은 문서 집합에서 원문을 보고 만든 질문으로 측정한 차이를 통계적으로 확정된 우열이나 일반적인 한국어 성능으로 확대할 수는 없다.

다음에는 독립적으로 모은 실사용 질문과 더 많은 문서로 같은 비교를 해보려 한다. 정답 파일과 여러 근거 구간을 별도로 검수하고 제목을 뺐을 때의 변화도 확인할 필요가 있다. 파서와 청크 구성을 고친 뒤 키워드 검색을 결합하고 리랭커를 붙이는 비교는 그다음이다. 최종 답변의 근거 일치 여부와 종단 지연도 함께 재야 한다.

운영 구성은 기존 서비스를 유지하면서 KURE-v3를 한 번 로딩하는 별도 Sentence Transformers API를 두는 쪽을 검토하고 있다. 모델 버전과 질문/문서 전처리를 API 안에서 고정하고 소규모 배치와 동시 요청 제한을 적용하는 구상이다. 인증과 상태 확인, 재시작 구성까지 포함해 실제 부하에서 검증해야 한다.

색인에는 본문뿐 아니라 문서 버전과 청크의 원문 위치, 접근 권한이 필요하다. 검색 결과의 내용을 LLM에 넘기기 전에 권한을 확인하고 편집과 삭제도 색인에 반영해야 한다. 원문 변경이 항상 버전 증가나 수정 시각 변화로 잡히는지부터 확인해야 하므로 수정 시각 폴링만으로 동기화를 끝낼 생각은 없다. pgvector도 이 단계에서 검토할 선택지다. 아직 설치하거나 운영 색인을 구축하지 않았다.

지금 정한 것은 다음 검증에 먼저 가져갈 모델이다. 실제 질문에서도 KURE의 근거 검색 이점이 남는지와 Qwen의 파일 검색 이점이 얼마나 유용한지가 다음 선택을 바꿀 수 있다.
